# 1.6 Schedule and booking

## Goal

Book an appointment for a practitioner, refusing it when it falls outside
their working hours or overlaps an appointment already booked.

Roadmap row: *`Schedule::book` (no overlap, within hours)*. Concepts:
`thiserror`, `?`, ownership in APIs.

## What changed

- `src/schedule.rs`: `Schedule` and `BookingError`, replacing the step 1.1
  placeholder. See [schedule](../reference/schedule.md).
- `src/appointment.rs`: the `Appointment` entity. See
  [appointment](../reference/appointment.md).
- `Cargo.toml`: the `thiserror` dependency.
- `tests/schedule.rs`.

## Rust concepts

### Deriving errors with `thiserror`

```rust,ignore
#[derive(Debug, Clone, Copy, PartialEq, Eq, Error)]
pub enum BookingError {
    #[error("appointment would end after the latest supported time")]
    OutOfRange,
    #[error("appointment is outside the practitioner's working hours")]
    OutsideWorkingHours,
    #[error("appointment overlaps an existing appointment")]
    Overlaps { existing: TimeSlot },
}
```

Steps 1.2 to 1.5 wrote `impl fmt::Display` with a `match` and an empty
`impl Error` by hand. `thiserror` is a derive macro that writes the same
code from the `#[error("...")]` attributes. The result is an ordinary
`std::error::Error`; callers can't tell which way it was written, and
`thiserror` never shows up in the public API. The older errors keep the
manual version, so both styles can be compared side by side.

Book: [Macros](https://doc.rust-lang.org/book/ch20-05-macros.html) (derive
macros) and [the `thiserror` docs](https://docs.rs/thiserror).

### `?` with `ok_or`

```rust,ignore
let slot = appointment_type
    .slot_starting_at(start)
    .ok_or(BookingError::OutOfRange)?;
```

`slot_starting_at` returns an `Option`, but `book` returns a `Result`, so
`?` can't use the `None` directly. `ok_or` turns `None` into
`Err(BookingError::OutOfRange)` and `Some(slot)` into `Ok(slot)`. Then `?`
either unwraps the slot or returns the error from `book` early.

Book: [Propagating Errors](https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html#propagating-errors).

### Ownership in, a borrow out

```rust,ignore
pub fn book(
    &mut self,
    start: DateTime<Utc>,
    appointment_type: AppointmentType,
) -> Result<&Appointment, BookingError>
```

- `appointment_type` is taken **by value**, because the schedule stores it
  inside the new `Appointment`. A caller that wants to keep its own copy
  calls `.clone()`; the cost of the copy is visible at the call site.
  `Schedule::new` takes `WorkingHours` by value for the same reason.
- `&mut self` means nobody else can read or change the schedule during the
  call.
- The returned `&Appointment` borrows from the schedule. While the caller
  holds it, the schedule stays borrowed, so the compiler refuses another
  `book` until the reference is no longer used. The elided lifetime ties the
  output to `self`.
- If a check fails, `appointment_type` is dropped and the schedule is left
  unchanged: all checks run before the `insert`.

Book: [What Is Ownership?](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)
and [References and Borrowing](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html).

### `pub(crate)` constructors

`Appointment::scheduled` is `pub(crate)`: code inside `clinic-domain` can
call it, other crates can't. With private fields too, the only way to get
an `Appointment` from outside the crate is `Schedule::book`, so every
appointment passed the booking rules.

Book: [Paths for Referring to an Item in the Module Tree](https://doc.rust-lang.org/book/ch07-03-paths-for-referring-to-an-item-in-the-module-tree.html).

### Keeping a `Vec` sorted with `partition_point`

```rust,ignore
let index = self
    .appointments
    .partition_point(|appointment| appointment.slot().start() <= slot.start());
self.appointments
    .insert(index, Appointment::scheduled(appointment_type, slot));
```

`partition_point` binary-searches a sorted slice for the first element where
the closure turns false. Inserting there keeps the appointments sorted
without re-sorting.

## Design choices worth questioning

- **The check order is part of the contract.** Range, then working hours,
  then overlap. A slot that is both outside the hours and overlapping gets
  `OutsideWorkingHours`. A test pins this down.
- **`Overlaps` names the slot it collided with,** so a later HTTP response
  can say what is in the way. The message doesn't include it, because
  `TimeSlot` has no `Display` yet.
- **Every booked appointment blocks its slot.** There is no way to cancel
  through `Schedule` yet. When that arrives, cancelled appointments should
  stop blocking, and `AppointmentStatus::transition_to` will decide which
  moves are allowed.
- **No `PractitionerId` on `Schedule`.** The schedule doesn't need it to
  apply the rules. The storage in M2 will key schedules by practitioner.
- **No way to rebuild a `Schedule` from stored appointments yet.** M2 will
  need one when it loads a schedule from storage, and it must re-check the
  rules or trust the store.
- **Overlap is a linear scan.** Appointments are sorted, so a binary search
  would work, but a single day's agenda is small.
- **`thiserror` only for the new error.** Migrating the older errors is a
  separate, mechanical change.

## Tests

Booking inside either shift works, including one ending exactly at a
shift's end and back-to-back appointments. The returned appointment has the
type, the slot and the `Scheduled` status, and the schedule keeps it.
Bookings in the lunch gap, past the end of a shift, on a day with no shift,
or with empty working hours give `OutsideWorkingHours`. Overlapping and
identical starts give `Overlaps` with the existing slot. Working hours are
checked before overlap. A start at the latest representable time gives
`OutOfRange`. A rejected booking leaves the schedule unchanged, and
appointments come back sorted by start. The error has messages and
implements `Error`. Two `compile_fail` doctests prove `Schedule` and
`Appointment` can't be built with a struct literal.
