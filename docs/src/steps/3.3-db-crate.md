# 3.3 The db crate and Postgres

## Goal

Bring a real database into the project, without using it yet. This step
adds a Postgres container for development and tests, a `db` crate that
opens a connection pool, the first migration, which creates the platform
schema and `platform.clinics`, a way to look a clinic up there, and
`SchemaName`, the name of a clinic's own schema, derived only from its
`ClinicId`. It also adds a test harness that gives every database test a
fresh database of its own.

The server still runs on the in-memory storage. Step 3.4 provisions clinic
schemas and opens tenant transactions, 3.5 writes the Postgres adapters for
the ports, and 3.7 switches the server over. The walkthrough's transcript
doesn't change.

The domain gains a `clinic` module, because the table stores something the
domain hadn't modeled: a clinic's slug and whether it's active.

Roadmap row: *`db` crate and `compose.yaml` (Postgres): pool, platform
migrations, `platform.clinics`, `SchemaName` derived from `ClinicId`. DB
test harness*. Concepts: sqlx pool, `migrate!`, `query!` and the offline
`.sqlx` cache, integration tests against Docker.

## Rust concepts

### A pool of connections

```rust,ignore
pub async fn connect(url: &str) -> Result<PgPool, StorageError> {
    PgPoolOptions::new()
        .max_connections(MAX_CONNECTIONS)
        .acquire_timeout(ACQUIRE_TIMEOUT)
        .connect(url)
        .await
        .map_err(StorageError::new)
}
```

Opening a Postgres connection takes a network round trip, authentication
and a server process, so a server keeps a few open and lends them out. A
`PgPool` is that set of connections. A query borrows one (`&pool` is enough,
because the pool locks internally) and gives it back when it's done.

`PgPool` is a handle around an `Arc`, so cloning it is cheap and every clone
shares the same connections. That's why `Platform` takes a `PgPool` by
value, and why 3.7's `AppState` can hold one without a `Mutex`.

`connect` opens the first connection straight away, so a wrong URL or a
stopped server fails at startup. A refused connection isn't given up on
at once: sqlx retries until `acquire_timeout`, which is why the test
against a closed port takes 5 seconds.

Every sqlx error becomes a `StorageError`, the error the ports from step
3.1 already return. `map_err(StorageError::new)` works because `new` takes
anything that converts into `Box<dyn Error + Send + Sync>`, and
`sqlx::Error` does.

Docs: sqlx's [`PgPoolOptions`](https://docs.rs/sqlx/0.9/sqlx/pool/struct.PoolOptions.html).

### `migrate!`: migrations compiled into the binary

```rust,ignore
pub static PLATFORM_MIGRATOR: Migrator = sqlx::migrate!("migrations/platform");
```

A *migration* is a SQL file that changes the schema one step. Each has a
version, taken from its file name (`0001_...`). `migrate!` is a macro that
runs when the crate compiles: it reads every file in the directory and
expands to a `Migrator` value holding their text and checksums. The binary
carries its migrations, so the server never needs the `.sql` files at run
time.

`Migrator::run` records each migration it applies in a `_sqlx_migrations`
table, and skips the ones already there. That's why
`migrating_twice_is_harmless`. If an applied file is edited later, its
checksum no longer matches and `run` refuses, which protects a database
from history being rewritten.

Cargo rebuilds a crate when its Rust sources change, but it doesn't know
that `migrate!` read the `migrations/` directory. `build.rs` tells it:

```rust,ignore
fn main() {
    println!("cargo:rerun-if-changed=migrations");
}
```

A *build script* is a program Cargo compiles and runs before compiling the
crate. Its `cargo:` lines on stdout give instructions to Cargo.

Book: [Macros](https://doc.rust-lang.org/book/ch20-05-macros.html). Cargo:
[Build scripts](https://doc.rust-lang.org/cargo/reference/build-scripts.html).

### `query!`: SQL checked by the compiler

```rust,ignore
let row = sqlx::query!(
    "SELECT id, slug, status FROM platform.clinics WHERE id = $1",
    key,
)
.fetch_optional(&self.pool)
.await
.map_err(StorageError::new)?;

row.map(|row| clinic_from_row(row.id, &row.slug, &row.status))
    .transpose()
```

While the crate compiles, `query!` connects to the database in
`DATABASE_URL`, asks Postgres to prepare the statement, and reads back the
types of the parameters and columns. A misspelled column, a missing table
or a parameter of the wrong type is a compile error, not a failure at run
time.

It then generates an *anonymous record* type with one field per column,
typed from the database's answer: `id: i64` for `bigint`, `slug: String`
and `status: String` for `text`. A column Postgres says can be null would
be an `Option<_>`. Here every column is `NOT NULL`, so none is. That's why
`row.slug` is a plain `String`.

`fetch_optional` gives `Option<Record>`. `map` turns that into
`Option<Result<Clinic, _>>`, and `transpose` swaps it into the
`Result<Option<Clinic>, _>` the method returns.

The record is all the macro can check. `status` is any `text` as far as
Rust knows, so `clinic_from_row` still maps `'active'` and `'suspended'` to
`ClinicStatus` by hand, and rejects anything else as a `StorageError`.

Docs: [`sqlx::query!`](https://docs.rs/sqlx/0.9/sqlx/macro.query.html).
Book: [`Option`](https://doc.rust-lang.org/std/option/enum.Option.html#method.transpose)
has `transpose`.

### The offline cache: `.sqlx/`

A database at compile time is fine on a laptop running compose, but not
for a CI job that only runs `cargo clippy`. So `cargo sqlx prepare
--workspace`, from sqlx-cli, compiles the workspace once against the
database and saves what Postgres said about each query to a JSON file in
`.sqlx/`:

```text
.sqlx/query-96831ea5....json   "SELECT id, slug, status FROM platform.clinics WHERE id = $1"
```

When `DATABASE_URL` isn't set, or `SQLX_OFFLINE=true` is, `query!` reads
that file instead of asking the database. The cache is committed. After a
query or a migration changes, `cargo sqlx prepare --workspace` updates it,
and `cargo sqlx prepare --workspace --check` fails if it's stale, which is
what CI will run in step 3.8.

### `#[sqlx::test]`: a database per test

```rust,ignore
#[sqlx::test(
    migrator = "clinic_db::migrate::PLATFORM_MIGRATOR",
    fixtures("clinics")
)]
async fn finds_a_suspended_clinic(pool: PgPool) {
    let platform = Platform::new(pool);
    // ...
}
```

`#[sqlx::test]` is an attribute macro that wraps an `async` test. Before
the test runs, it connects to `DATABASE_URL`, creates a new database just
for this test, runs the migrator into it, loads the fixture
`tests/fixtures/clinics.sql`, and passes the test a pool for that database.
When the test passes, the database is dropped. When it fails, it's kept so
you can look at it.

Each test starts from a known state and can't see another's rows, so the
tests run in parallel without cleaning up after each other.
`migrations = false` gives an empty database instead, which is how
`migrating_twice_is_harmless` tests the migrator itself. A test can also
ask for the connection options, `PgConnectOptions`, instead of a pool. That
gives `connects_to_a_running_server` a URL to pass to `connect`.

If Postgres isn't running, every one of these tests fails. None of them
skips. A green `cargo test` therefore always includes the database tests,
and from 3.4 on, the isolation test.

Docs: [`sqlx::test`](https://docs.rs/sqlx/0.9/sqlx/attr.test.html).

### SQL that sqlx 0.9 won't run

The first version of the constraint tests built each `INSERT` with
`format!`. It didn't compile:

```text
error[E0521]: borrowed data escapes outside of function
```

In sqlx 0.9, `sqlx::query` takes only SQL that implements `SqlSafeStr`, and
only `&'static str` does: a literal written in the source. A `String` built
at run time has to be wrapped in `AssertSqlSafe(..)`, which says that a
person checked it can't carry an injection. The tests now bind every value
as a parameter instead (`$1`, `.bind(slug)`), which is the right way:

```rust,ignore
sqlx::query(
    "INSERT INTO platform.clinics (id, slug, schema_name, status) VALUES ($1, $2, $3, $4)",
)
.bind(id)
.bind(slug)
```

A schema name is the one thing that can't be bound, which is why it gets a
type of its own.

### `SchemaName`: a string with only one source

```rust,ignore
pub struct SchemaName(String);

impl From<ClinicId> for SchemaName {
    fn from(clinic: ClinicId) -> Self {
        Self(format!("clinic_{}", clinic.value()))
    }
}
```

Step 3.4 runs `SET LOCAL search_path TO clinic_42`. Postgres can bind
values as `$1`, but not names of schemas or tables, so the name is written
into the SQL text, and would be wrapped in `AssertSqlSafe`. If it came
from a request, `42; DROP TABLE ...` would be SQL.

The field is private and the only way in is `From<ClinicId>`, so every
`SchemaName` is `clinic_` followed by digits: no quotes, no spaces, and no
semicolons. A `compile_fail` doctest shows that `SchemaName(String::from(..))`
is rejected (E0423). Implementing `From` also gives `.into()` for free:
`let name: SchemaName = clinic.into();`.

The database enforces the same rule. `platform.clinics` has
`CHECK (schema_name = 'clinic_' || id)`, so no other path, such as a
manual `INSERT`, can record a mismatched name.

Book: [Defining Methods](https://doc.rust-lang.org/book/ch05-03-method-syntax.html),
and `From` in [Rust by Example](https://doc.rust-lang.org/rust-by-example/conversion/from_into.html).

### `i64::try_from`: when the column is smaller than the type

`ClinicId` holds a `u64`, but Postgres has no unsigned integers, and the
column is a `bigint`, an `i64`. Half the `u64` range doesn't fit:

```rust,ignore
// The column is a bigint, so an id above `i64::MAX` can't be in the table.
let Ok(key) = i64::try_from(id.value()) else {
    return Ok(None);
};
```

`TryFrom` is `From` for conversions that can fail, returning a `Result`.
`let ... else` binds the `Ok` value or runs the `else` block, which must
leave the function. A clinic whose id can't be stored can't exist, so the
lookup answers `None` without asking the database. Reading back, the row's
`i64` becomes a `u64` with `u64::try_from`. `CHECK (id >= 0)` means it never
fails, but if it did, the result would be a `StorageError`, not a panic.

Book: [`let ... else`](https://doc.rust-lang.org/book/ch06-03-if-let.html#staying-on-the-happy-path-with-letelse).
Docs: [`TryFrom`](https://doc.rust-lang.org/std/convert/trait.TryFrom.html).

## Design choices worth questioning

- **The domain got a `Clinic`, without a plan.** The roadmap put `plan` in
  `platform.clinics`, but nothing reads it until M6 or M8, and no tiers
  have been defined. The column comes when a plan changes behavior. The
  text forms (`'active'`) stay in the db crate: the domain knows
  `ClinicStatus`, and only the adapter knows how it's spelled in a table.
- **`schema_name` is stored, although it follows from `id`.** It's
  redundant by design: it makes `platform.clinics` readable on its own in
  `psql`, and the `CHECK` keeps it from ever disagreeing. If clinics later
  move to databases of their own (M8), this is where a location would
  live.
- **`SchemaName` lives in the db crate, not the domain.** It's a SQL
  identifier, an adapter's concern. The domain only knows `ClinicId`.
- **Platform migrations are tracked in `public._sqlx_migrations`.** They
  create the `platform` schema, so sqlx can't keep its table there before
  the first one runs. Tenant migrations in 3.4 will keep a
  `_sqlx_migrations` in each clinic's schema, which gives per-schema status
  for free.
- **`Platform` is not a port yet.** No use case needs a clinic lookup until
  3.7, when an unknown clinic becomes a 404. Adding a port now would mean
  guessing its shape.
- **An id above `i64::MAX` gives `None`, not an error.** It can't name a
  stored clinic, so "no such clinic" is the true answer. Provisioning in 3.4
  must refuse such an id.
- **`.env` isn't committed.** It holds only the local container's
  throwaway password, but keeping env files out of git is a rule worth not
  bending. `.env.example` is committed instead. Without a `.env`, the build
  uses the offline cache, but the database tests fail.
- **With a `.env`, a stopped Postgres breaks the build.** `query!` tries
  the database first when `DATABASE_URL` is set. `SQLX_OFFLINE=true` makes
  it use the cache.
- **Port 5433, not 5432.** It leaves the default port free for any other
  Postgres on the machine, and binds to `127.0.0.1` only.
- **No TLS.** The database is a local container. A TLS feature
  (`tls-rustls`) gets added when the server talks to a hosted one.

## Tests

`crates/domain/tests/clinic.rs`: a valid slug; trimming and lowercasing;
`Display`; empty and blank slugs; 63 bytes accepted and 64 refused;
underscores, spaces, dots, accented letters, slashes and semicolons
refused; leading, trailing and doubled hyphens refused; error messages; and
a `Clinic` keeps its parts. A `compile_fail` doctest (E0451) shows that the
fields of `Clinic` are private.

`crates/db/tests/schema_name.rs`, with no database: `clinic_42` and
`clinic_0`; `Display`; the name for `u64::MAX` is 27 bytes, under
Postgres's 63; every name is only `[a-z0-9_]` and starts with a letter; and
clinics 1 and 11 get different names. A `compile_fail` doctest (E0423)
shows a `SchemaName` can't be built from a string.

`crates/db/tests/migrations.rs`: migrating twice works and leaves an empty
table; a new clinic is `active` by default. The table refuses, with the
SQLSTATE checked, a `schema_name` that doesn't match the id, malformed
slugs, a 64-byte slug, an unknown status and a negative id (all `23514`,
check violation), and a duplicate slug (`23505`, unique violation).

`crates/db/tests/platform.rs`, with the fixture of clinics 1 and 2: an
active and a suspended clinic are found with their slug and status; an
unknown id is `None`; `u64::MAX` is `None`; and a closed pool is a
`StorageError`.

`crates/db/tests/pool.rs`: connecting to a closed port and to a string that
isn't a URL both fail with `StorageError`; connecting to the test database
works and runs `SELECT 1`.

The DB tests were also run with Postgres stopped: every `#[sqlx::test]`
panicked.

## See it run

```sh
cp .env.example .env
docker compose up -d --wait
cargo sqlx migrate run --source crates/db/migrations/platform
cargo test -p clinic-db
```

The development database now has the platform schema:

```sh
docker compose exec postgres psql -U clinic -c '\d platform.clinics'
```

```text
                            Table "platform.clinics"
   Column    |           Type           | Collation | Nullable |    Default
-------------+--------------------------+-----------+----------+----------------
 id          | bigint                   |           | not null |
 slug        | text                     |           | not null |
 schema_name | text                     |           | not null |
 status      | text                     |           | not null | 'active'::text
 created_at  | timestamp with time zone |           | not null | now()
Indexes:
    "clinics_pkey" PRIMARY KEY, btree (id)
    "clinics_slug_key" UNIQUE CONSTRAINT, btree (slug)
Check constraints:
    "clinics_check" CHECK (schema_name = ('clinic_'::text || id))
    "clinics_id_check" CHECK (id >= 0)
    "clinics_slug_check" CHECK (length(slug) <= 63 AND slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'::text)
    "clinics_status_check" CHECK (status = ANY (ARRAY['active'::text, 'suspended'::text]))
```

The table rejects a schema name that doesn't follow from the id:

```sh
docker compose exec postgres psql -U clinic -c \
  "INSERT INTO platform.clinics (id, slug, schema_name) VALUES (1, 'centro', 'public')"
```

```text
ERROR:  new row for relation "clinics" violates check constraint "clinics_check"
DETAIL:  Failing row contains (1, centro, public, active, 2026-11-23 19:04:33.391967+00).
```

The server and the walkthrough don't change in this step: `cargo run -p
clinic` still serves from memory.
