# 2.5 Serving HTTP: the agenda route and a real server

## Goal

Make the API something you can reach with curl. Step 2.4 built the router
as a library that only tests could call. This step does three things:

- adds the second route, `GET /practitioners/{id}/agenda`, in front of the
  `practitioner_agenda` query from step 2.2
- turns the `clinic` binary into the server that serves both routes, with a
  graceful shutdown
- replaces the scripted day with a curl walkthrough, which a test replays
  against the real binary over a real socket

Roadmap row: *`GET /practitioners/{id}/agenda`; the `clinic` binary serves
HTTP; the scripted day becomes a curl walkthrough*. Concepts: composition
root, graceful shutdown, integration tests over HTTP.

- `crates/api` (see [api](../reference/api.md)):

  - `error.rs`: `ApiError` gains `InvalidPath`, `InvalidQuery`,

    `appointments.rs` so both handlers share it.
- `crates/clinic` (see [clinic](../reference/clinic.md)):
  - `main.rs` is now the server. The scripted day is gone; the interlude and
    steps 1.8 to 2.3 show its output.
  - `seed.rs` (new): the demo clinics the server starts with.
  - New dependencies: `clinic-api`, `axum` 0.8, and `tokio` 1 with

  - New test-only dependencies: `hyper` 1 with `client` and `http1`,

    `signal-hook-registry` and `errno` for tokio's signals.
- Tests:
  - `crates/api/tests/agenda.rs` (new) has 10 cases.

  - `crates/clinic/tests/run.rs` is replaced by `walkthrough.rs` (1 test),
    `server.rs` (3 tests) and `common/mod.rs`.
  - `crates/clinic/tests/expected-output.txt` is now the walkthrough's
    transcript.
- The domain and `app` are unchanged.
- [Roadmap](../roadmap.md): each step now extends the walkthrough instead

## Rust concepts

### `#[tokio::main]` and `ExitCode`

```rust,ignore
#[tokio::main]
async fn main() -> ExitCode {
    match run().await {
        Ok(()) => ExitCode::SUCCESS,
        Err(error) => {
            eprintln!("clinic: {error}");
            ExitCode::FAILURE
        }
    }
}
```

`main` can't be `async` on its own, because something has to poll the
future. `#[tokio::main]` is a macro that rewrites this into a plain `main`
that builds a multi-threaded tokio runtime and runs the body on it with
`block_on`. It's the same thing `#[tokio::test]` did for the tests in step
2.4.

`main` returns `ExitCode`, not `Result<(), Box<dyn Error>>` like the
scripted day did. A `Result` from `main` prints the error with `Debug`,
which shows `Error: "CLINIC_ADDR \"nope\" isn't..."` with quotes and
escapes. Matching on the result keeps the message readable and makes the
exit code explicit.

Reference: [`tokio::main`](https://docs.rs/tokio/1/tokio/attr.main.html),
[`ExitCode`](https://doc.rust-lang.org/std/process/struct.ExitCode.html).

### The composition root

```rust,ignore
async fn run() -> Result<(), Box<dyn Error>> {
    let addr = listen_addr()?;
    let shutdown =
        shutdown_signal().map_err(|error| format!("can't listen for shutdown signals: {error}"))?;
    let state = seed::demo_state()?;

    let listener = TcpListener::bind(addr)
        .await
        .map_err(|error| format!("can't listen on {addr}: {error}"))?;
    eprintln!("clinic listening on http://{}", listener.local_addr()?);

    axum::serve(listener, clinic_api::router(state))
        .with_graceful_shutdown(shutdown)
        .await?;
    Ok(())
}
```

This is the only place that knows which adapters exist. `seed::demo_state`
picks the in-memory ones and fills them. `clinic_api::router` gets an
`AppState` and never learns what's inside. In M3 this function changes to
build Postgres adapters, and no handler or use case changes.

`TcpListener::bind` is where the I/O starts: it asks the OS for the port.
`.await` lets the runtime do other work while that happens. `axum::serve`
then loops forever: it accepts a connection, hands it to hyper, and runs the
router for each request on its own task.

`map_err(|error| format!(...))` adds context to an error before `?`
returns it. `?` converts a `String` into `Box<dyn Error>` through
`From`, as in the
[interlude](interlude-running-the-clinic.md). The binary only reports errors, so a
string is enough.

### Graceful shutdown with `select!`

```rust,ignore
fn shutdown_signal() -> io::Result<impl Future<Output = ()>> {
    let mut interrupt = signal(SignalKind::interrupt())?;
    let mut terminate = signal(SignalKind::terminate())?;

    Ok(async move {
        tokio::select! {
            _ = interrupt.recv() => {}
            _ = terminate.recv() => {}
        }
        eprintln!("clinic shutting down");
    })
}
```

`with_graceful_shutdown` takes any future. When it finishes, axum stops
accepting connections, waits for the requests in progress, and then
`serve(...).await` returns. Without it, Ctrl-C kills the process
mid-request.

`tokio::select!` polls several futures at once and runs the arm of
whichever finishes first. The others are dropped. Here it waits for either
signal: SIGINT is Ctrl-C in a terminal, and SIGTERM is what `kill`,
`docker stop` and Kubernetes send.

The function isn't `async`. It installs both handlers right away, where
`?` can report a failure before the server starts, and then returns a
future for the waiting. An `async fn` would do nothing until polled, and a
failure inside `with_graceful_shutdown` would have nowhere to go. The
return type `io::Result<impl Future<Output = ()>>` says "an error, or some
future": `impl Trait` from step 2.2, and an `async` block, which is a
future with no name. `move` hands the two signal streams to that block.

`tokio::signal::unix` exists only on Unix, so it's behind `#[cfg(unix)]`,
and another `shutdown_signal` handles only Ctrl-C on other platforms.
`#[cfg(...)]` removes the item from compilation entirely, so each platform
sees one function.

Reference: [`select!`](https://docs.rs/tokio/1/tokio/macro.select.html),
[graceful shutdown in axum](https://docs.rs/axum/0.8/axum/serve/struct.WithGracefulShutdown.html).
Book: [Futures and the async syntax](https://doc.rust-lang.org/book/ch17-01-futures-and-syntax.html).

### `Path` and `Query`, with their rejections as `Result`

```rust,ignore
pub async fn agenda(
    State(state): State<AppState>,
    ClinicHeader(clinic): ClinicHeader,
    id: Result<Path<u64>, PathRejection>,
    params: Result<Query<AgendaParams>, QueryRejection>,
) -> Result<Json<AgendaBody>, ApiError> {
    let Path(id) = id?;
    let Query(params) = params?;
```

`Path<u64>` parses the `{id}` in the route into a `u64`. `Query<T>` reads
the query string into any `T: Deserialize`, with the same serde derive the
JSON body uses. Like `Json` in step 2.4, both are taken as `Result`, so
`/practitioners/abc/agenda` gets a JSON `invalid_path` error instead of
axum's plain text. `ApiError` gets a `From` impl for each rejection, which
is all `?` needs.

`AgendaParams` uses `deny_unknown_fields` too, so `?from=..&to=..&room=3`
is refused rather than ignored. `from` and `to` are `DateTime<Utc>`, read
from RFC 3339 like the body's `start`. The catch is the query string's own
encoding: `+` means a space there, so `10:00:00+01:00` arrives as
`10:00:00 01:00` and fails to parse. A client must send `%2B`, or use `Z`
or a negative offset. The docs say so, and a test sends `%2B01:00`.

The range check stays in the domain: `TimeSlot::new(params.from,
params.to)?` refuses a range that doesn't end after it starts, and
`ApiError::InvalidRange(#[from] TimeSlotError)` turns that into 422.

### A temporary guard

```rust,ignore
let appointments = practitioner_agenda(state.lock()?.schedules.as_ref(), &access, query)?;
```

`book` in step 2.4 kept its guard in a variable for the whole use case.
Here the guard is a *temporary*. Rust drops a temporary at the end of the
statement that created it, so the lock is held exactly while
`practitioner_agenda` runs, and released before the JSON is built.
`practitioner_agenda` returns owned `Appointment`s (step 2.2), so nothing
borrowed from the store outlives the lock.

Reference: [temporary scopes](https://doc.rust-lang.org/reference/destructors.html#temporary-scopes).

### Port 0 and the real address

The tests run many servers at once, and a fixed port would collide. Binding
`127.0.0.1:0` asks the OS for any free port, and
`listener.local_addr()` says which one it got. The server prints that line
to stderr, and the test reads it:

```rust,ignore
let mut child = Command::new(env!("CARGO_BIN_EXE_clinic"))
    .env("CLINIC_ADDR", "127.0.0.1:0")
    .stdout(Stdio::piped())
    .stderr(Stdio::piped())
    .spawn()?;
let mut stderr = BufReader::new(child.stderr.take().unwrap());
stderr.read_line(&mut line)?;
let addr = line.trim_end().strip_prefix(LISTENING)...;
```

`read_line` blocks until the server has bound its port, so there's no
`sleep` and no polling. The line goes to stderr because stdout is for a
program's output, and a server has none: logs go to stderr. A test checks
that stdout stays empty.

### `Drop` as a safety net

```rust,ignore
impl Drop for Server {
    fn drop(&mut self) {
        let _ = self.child.kill();
        let _ = self.child.wait();
    }
}
```

When an assertion fails, the test panics and its locals are dropped while
the stack unwinds. Without this, every failing test would leave a server
running. `wait` reaps the process so it doesn't linger as a zombie.
Errors are ignored with `let _ =`: after `Server::stop` the process is
already gone, and there's nothing useful to do about a failure while
panicking anyway.

Book: [Running code on cleanup with `Drop`](https://doc.rust-lang.org/book/ch15-03-drop.html).

### hyper's low-level client

```rust,ignore
let stream = TcpStream::connect(self.addr).await?;
let (mut sender, connection) =
    hyper::client::conn::http1::handshake(TokioIo::new(stream)).await?;
tokio::spawn(connection);

let response = sender.send_request(request).await?;
```

This is the client half of what axum uses as a server. `handshake` splits
one TCP connection into two parts. `sender` sends requests. `connection` is
a future that moves bytes between the socket and `sender`, and someone has
to poll it, so `tokio::spawn` runs it as its own task. `TokioIo` adapts
tokio's socket to the I/O traits hyper is written against.

The request is the same `http::Request` the `oneshot` tests build, with a
`Full<Bytes>` body. The difference is that it now goes through a real
socket, hyper's HTTP/1.1 parser and the real `main`.

Reference: [hyper client guide](https://hyper.rs/guides/1/client/basic/).

## Design choices worth questioning

- **The walkthrough is a Rust test, not a shell script.** A script of curl
  commands would read more naturally, but it needs `bash` and `curl`, and
  its output would depend on the curl version. The test prints each
  request as the equivalent curl command, so the transcript is still a
  script you can copy, and `cargo test` runs it anywhere.
- **The transcript shows bodies exactly as sent.** That means one long line
  of JSON for an agenda. Pretty-printing would read better, but it would
  re-sort the keys (serde_json's `Value` keeps them sorted), and the golden
  file would no longer show what clients get.
- **Regenerating the golden file is an env var.** `UPDATE_EXPECTED=1` makes
  the test write the file instead of comparing. Forgetting to review the
  diff afterwards is the risk; `git diff` is the review.
- **An unknown practitioner in the path is 404; in a body it's 422.** Both
  have the same code, `unknown_practitioner`, so clients match on one
  thing. The status follows HTTP: the path names the resource.
- **`from` and `to` are required.** There's no "today" without a clock, and
  the domain has none. A default range would also make caching and paging
  harder to add later.
- **Reads take the same `Mutex` as writes.** Two agenda reads wait for each
  other, which an `RwLock` would avoid. In memory the lock is held for
  microseconds, and M3 replaces it with Postgres transactions, so it isn't
  worth the change now.
- **Configuration is one env var, parsed by hand.** A CLI crate such as
  `clap` would be one more dependency for one setting. `CLINIC_ADDR` takes
  an IP address, not a host name: `SocketAddr` doesn't resolve names, and
  resolving would be I/O at startup for no gain.
- **The seed is fixed data in code.** There's no endpoint for hours or
  appointment types yet. Step 2.6 adds the hours endpoint, and M3 moves
  storage to Postgres, where the seed becomes a migration or a script.
- **No JSON for unknown routes.** `GET /nope` gets axum's empty 404, and
  the wrong method gets a plain 405. A `fallback` handler returning
  `ApiError` would fix both, and it's a small follow-up.
- **In-flight requests during shutdown aren't tested.** The test checks
  that SIGTERM exits cleanly, not that a slow request finishes first.
  Every handler today returns in microseconds, so such a test would need a
  route made only for it.

## Tests

`crates/api/tests/agenda.rs` books two appointments into practitioner 1 at
clinic 1, 11:00 and then 09:00, through `POST /appointments`, and reads
the agenda:

- the full shift lists both in order of start, in the exact JSON shape
- a range that only partly overlaps an appointment still includes it
- a range between them is 200 with an empty list
- offsets are read as UTC, including `%2B01:00`
- clinic 2 asking for clinic 1's practitioner, and an unknown
  practitioner, are both 404 `unknown_practitioner`
- a missing or invalid `X-Clinic-Id` is 400, as on POST
- an `{id}` of `abc`, `-1` or `1.5` is 400 `invalid_path`
- a missing `from` or `to`, a value that isn't a timestamp, and an unknown
  parameter are 400 `invalid_query`
- a reversed or empty range is 422 `invalid_range`

The table test in `appointments.rs` now also covers `invalid_range` (422)
and the agenda's `unknown_practitioner` (404).

`crates/clinic/tests/walkthrough.rs` replays the walkthrough against the
real binary and compares the transcript. `crates/clinic/tests/server.rs`
checks that SIGTERM stops the server with exit code 0, `clinic shutting
down` on stderr and nothing on stdout, and that an address that doesn't
parse, or one already in use, exits with code 1 and a message.
