# 3.2 Tenant sessions

## Goal

Give every use case a unit of work before there's a database to need one.
Until now, one `tokio::sync::Mutex` in the api crate's `AppState` made "read
the schedule, book, save" atomic: a handler held it across the whole use
case. Postgres has no such lock. A use case needs a transaction around its
whole read-modify-write instead, and the ports had no way to say where one
starts and ends.

This step adds that shape. A use case asks a `Storage` to `begin` a session
at one clinic, reads and writes through the session's ports, and ends it
with `commit`. A session that's dropped without committing keeps nothing.
The clinic is named once, when the session begins, so the port methods lose
their `ClinicId` argument. In step 3.4 the `db` crate implements the session
by wrapping a `TenantTx`, and `api -> app` stays free of sqlx.

Nothing a client can see changes. The walkthrough's transcript is the same
byte for byte.

Roadmap row: *Tenant sessions: `begin(ClinicId)` returns a session that
implements the ports and ends with `commit`. Port methods lose their
`ClinicId` argument. No behavior change*. Concepts: associated types,
ownership of a unit of work, `Drop` as rollback.

## What changed

- `crates/app` (see [app](../reference/app.md#sessions)):
  - `ports.rs`: new `Storage` trait, with the associated type `Session` and
    `begin(clinic)`, and new `Session` trait, with `commit(self)`, that
    requires both ports. `ScheduleRepository::get` and `save` and
    `AppointmentTypes::find` lose their `ClinicId`. The E0038 doctest now
    uses `&dyn ScheduleRepository`; a new E0382 doctest uses a session after
    `commit`.
  - `in_memory.rs`: `InMemorySchedules` is gone. New `InMemoryStorage`
    (`new(types)`, `default`) keeps every clinic's schedules and appointment
    types behind one `Arc<tokio::sync::Mutex<_>>`, and new `InMemorySession`
    holds that lock from `begin` until it's committed or dropped, with its
    own saves waiting in a map until `commit`. `InMemoryAppointmentTypes` is
    now only the catalog a storage is created with; it doesn't implement the
    port any more.
  - `booking.rs`, `agenda.rs`, `hours.rs`: each use case takes one
    `&St` where `St: Storage + Sync`, instead of one or two adapters, and
    begins its own session. `book_appointment` and `set_weekly_hours`
    commit; `practitioner_agenda` drops its session. The error enums are
    unchanged: a failed `begin` or `commit` is their `Storage` variant.
  - `tokio` with the `sync` feature becomes a normal dependency; it was only
    a dev-dependency. It was already in `Cargo.lock`.
- `crates/api` (see [api](../reference/api.md#storage)):
  - `state.rs`: `AppState<St>` holds an `Arc<St>`, without a `Mutex`.
    `lock` is replaced by `storage`.
  - `lib.rs`, `appointments.rs`, `practitioners.rs`: `router` and the
    handlers take one type parameter, `St`, instead of `S` and `T`, and
    pass `state.storage()` to the use case.
- `crates/clinic`: `seed::demo_state` builds an `InMemoryStorage` and saves
  practitioner 1's schedule in a session that it commits.
- Tests: new `crates/app/tests/common/mod.rs` with `save_committed` and
  `stored`, used by every app test that seeds or reads a schedule.

## Rust concepts

### An associated type: each storage names its session

```rust,ignore
pub trait Storage {
    type Session: Session;

    fn begin(
        &self,
        clinic: ClinicId,
    ) -> impl Future<Output = Result<Self::Session, StorageError>> + Send;
}

pub trait Session: ScheduleRepository + AppointmentTypes + Send {
    fn commit(self) -> impl Future<Output = Result<(), StorageError>> + Send;
}
```

`begin` has to return *some* session, and each storage has its own: the
in-memory one returns an `InMemorySession`, and the database one will
return a session that wraps a transaction. `type Session: Session;` says
that every implementation of `Storage` picks one type, and that the type
must implement `Session`. The implementation fills it in:

```rust,ignore
impl Storage for InMemoryStorage {
    type Session = InMemorySession;

    async fn begin(&self, clinic: ClinicId) -> Result<InMemorySession, StorageError> {
        // ...
    }
}
```

Why not a type parameter, `trait Storage<S: Session>`? A type parameter
would let one storage implement `Storage<A>` and `Storage<B>`, and every
caller would have to say which. With an associated type there's exactly
one session per storage, so the use cases write only `St: Storage`, and
`St::Session` follows from it.

`Session: ScheduleRepository + AppointmentTypes + Send` makes the ports
*supertraits*: anything that's a `Session` has `get`, `save` and `find`,
so the use cases call them on the session directly. `Send` is there because
the session lives across the `.await`s of a handler, whose future must be
`Send`.

Book: [Specifying Placeholder Types in Trait Definitions with Associated Types](https://doc.rust-lang.org/book/ch20-02-advanced-traits.html#specifying-placeholder-types-in-trait-definitions-with-associated-types),
and [Using Supertraits](https://doc.rust-lang.org/book/ch20-02-advanced-traits.html#using-supertraits-to-require-one-traits-functionality-within-another-trait).

### `commit(self)`: owning the unit of work

```rust,ignore
let mut session = storage.begin(request.clinic).await?;
let mut schedule = session
    .get(request.practitioner)
    .await?
    .ok_or(BookAppointmentError::UnknownPractitioner)?;
// ... find the type, book ...
session.save(request.practitioner, schedule).await?;
session.commit().await?;
```

`get` and `find` borrow the session (`&self`), `save` borrows it mutably
(`&mut self`), and `commit` takes it by value (`self`). After `commit`, the
session has moved into the call and the variable can't be used again. A
use case can't save something after committing, and can't commit twice.
The `ports` module has a `compile_fail` doctest that tries, and fails with
E0382, "borrow of moved value".

The use case owns the session from `begin` to the end: the handler never
sees it. That puts the transaction boundary in the application layer, next
to the rules that need it, and keeps the handlers as one call each.

Book: [What Is Ownership?](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html),
especially "Ownership and Functions".

### `Drop` as rollback

Every `?` in `book_appointment` returns early, and so does a booking the
domain refuses. In each case `session` goes out of scope without being
committed, and Rust drops it. That's the rollback, and it needs no code:

```rust,ignore
pub struct InMemorySession {
    clinic: ClinicId,
    data: OwnedMutexGuard<Data>,
    pending: HashMap<PractitionerId, Schedule>,
}
```

Dropping a struct drops its fields. Dropping `pending` throws away what the
session saved, and dropping the `OwnedMutexGuard` unlocks the storage for
the next session. `InMemorySession` has no `impl Drop` of its own. sqlx's
`Transaction` does have one, which tells Postgres to roll back, and the
database session in 3.4 inherits it by holding a `Transaction`.

Not having `impl Drop` is also what lets `commit` take the session apart:

```rust,ignore
async fn commit(self) -> Result<(), StorageError> {
    let Self { clinic, mut data, pending } = self;
    data.schedules.extend(
        pending
            .into_iter()
            .map(|(practitioner, schedule)| ((clinic, practitioner), schedule)),
    );
    Ok(())
}
```

Moving fields out of a value whose type implements `Drop` is an error
(E0509), because `drop` would then run on a half-empty value.

The tests check both endings: a session dropped without `commit` leaves
nothing behind and keeps the earlier schedule, and a booking whose `commit`
fails leaves the stored schedule as it was.

Book: [Running Code on Cleanup with the `Drop` Trait](https://doc.rust-lang.org/book/ch15-03-drop.html).

### `lock_owned`: a guard that borrows nothing

```rust,ignore
async fn begin(&self, clinic: ClinicId) -> Result<InMemorySession, StorageError> {
    let data = Arc::clone(&self.data).lock_owned().await;
    Ok(InMemorySession { clinic, data, pending: HashMap::new() })
}
```

`self.data.lock().await` would return a `MutexGuard<'_, Data>` that borrows
`self`. A session holding it would borrow the storage, and couldn't be
returned from `begin` without a lifetime on `Session` and on every use case.
`lock_owned` takes an `Arc<Mutex<Data>>` by value instead, and its
`OwnedMutexGuard<Data>` keeps that `Arc` alive itself. The guard borrows
nothing, so the session is `'static` and is free to move around, as the
database session holding a pooled connection will be.

The lock moved here from the api crate. A session holds it from `begin` to
`commit` or drop, across every `.await` in the use case, which is the same
span the handlers used to hold it for. That's why behavior didn't change:
sessions still run one at a time. The api crate's `AppState` is now only
an `Arc<St>`.

Docs: tokio's [`Mutex::lock_owned`](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html#method.lock_owned).

## Design choices worth questioning

- **The use case begins and commits, not the handler.** The handler could
  begin a session and pass it in, which would let one request run two use
  cases in one transaction. Nothing needs that yet, and it would need its
  own `ApiError` variant for a failed `begin` and put the transaction
  boundary in the delivery layer. Requests keep their `clinic` field, and
  `begin` is the only place it's used.
- **The agenda doesn't commit.** It only reads, so it drops its session,
  which is a rollback. In Postgres that's as cheap as a commit for a
  read-only transaction. A test pins it: the agenda works with a storage
  whose `commit` always fails.
- **One lock for every clinic.** The in-memory storage still runs one
  session at a time, across clinics too. A lock per clinic would be closer
  to Postgres, but would change behavior in a step that promises none, and
  the in-memory storage goes away in 3.7.
- **A second `begin` in the same task waits forever.** The lock isn't
  re-entrant, and nothing stops a use case from beginning two sessions. No
  use case does, the docs say not to, and the database session will have
  its own version of the rule (two transactions don't see each other's
  writes).
- **`app` depends on tokio now.** Only its `sync` feature, which is plain
  data structures and no runtime or I/O. The alternative, a lock passed in
  from the api crate, would split the in-memory adapter across two crates.
- **Sessions keep `get` returning a whole schedule.** Loading only a date
  range is still a [known gap](../reference/app.md#not-yet), for the
  Postgres adapter in 3.5.

## Tests

`crates/app/tests/in_memory.rs`, rewritten around sessions: a committed
schedule is read back by a later session; a session sees its own
uncommitted save; a session dropped without `commit` saves nothing, and
keeps an earlier schedule; saving again replaces the schedule; a schedule
and an appointment type are invisible to a session at another clinic; and
clones of an `InMemoryStorage` share their data. The appointment type cases
find through a session.

`crates/app/tests/storage_errors.rs`: a `Faulty` storage wraps the in-memory
one and fails at one step: `Begin`, `Get`, `Find`, `Save` or `Commit`.
Booking fails with `Storage` at each of the five, and the stored schedule
has no appointment afterwards. Setting hours fails at each of its four
steps and stores nothing. The agenda fails if a session can't begin or
read, and works when `commit` would fail, because it never commits. The
`StorageError` tests are unchanged.

`crates/app/src/ports.rs`: two `compile_fail` doctests, `&dyn
ScheduleRepository` (E0038) and a session used after `commit` (E0382).

`crates/api/tests/storage_errors.rs`: storage that can't `begin` a session
gives the same 500s as before. `crates/api/tests/appointments.rs`:
`AppState<InMemoryStorage>` is `Clone + Send + Sync + 'static`.

The other app and api tests are the same cases, seeded through a
committed session. The walkthrough runs unchanged against
`expected-output.txt`.
