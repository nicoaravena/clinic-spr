# 1.7 Roles and access

## Goal

Decide what each member of a clinic's staff may access, so that only
practitioners can reach clinical content. Code that needs access should not
compile unless the check was made.

Roadmap row: *`Role` and permissions (only practitioners touch clinical
notes)*. Concepts: traits, types that make bad states unrepresentable.

## What changed

- `src/access.rs`: `Role`, the `Capability` trait, `ClinicalAccess`,
  `ScheduleAccess`, `AuditAccess` and `AccessDenied`. See
  [access](../reference/access.md).
- `src/lib.rs`: the new module.
- `tests/access.rs`.

## Rust concepts

### Defining and implementing a trait

```rust,ignore
pub trait Capability: Sized {
    const NAME: &'static str;

    fn grant(role: &Role) -> Option<Self>;
}

impl Capability for ClinicalAccess {
    const NAME: &'static str = "clinical content";

    fn grant(role: &Role) -> Option<Self> {
        match role {
            Role::Practitioner(practitioner) => Some(Self {
                practitioner: *practitioner,
            }),
            Role::Receptionist | Role::Administrator => None,
        }
    }
}
```

A trait names behaviour that several types share. Each capability
implements it with its own rule. `grant` has no `self`: it is an
*associated function* that builds a new value, like `new`. `NAME` is an
*associated const*, a value each implementation must provide. `Sized` is a
*supertrait*: returning `Option<Self>` needs the size of `Self` to be known
at compile time.

Book: [Traits: Defining Shared Behavior](https://doc.rust-lang.org/book/ch10-02-traits.html)
and [Advanced Traits](https://doc.rust-lang.org/book/ch20-02-advanced-traits.html)
(supertraits).

### A generic method with a trait bound

```rust,ignore
impl Role {
    pub fn grant<C: Capability>(&self) -> Result<C, AccessDenied> {
        C::grant(self).ok_or(AccessDenied {
            capability: C::NAME,
        })
    }
}
```

`C: Capability` means "any type that implements `Capability`". The caller
picks `C` with the turbofish, `role.grant::<ClinicalAccess>()`, or the
compiler infers it from where the result is used. The compiler generates one
copy of `grant` for each `C` (*monomorphization*), so there is no runtime
lookup. `ok_or` turns the `Option` into a `Result`, as in step 1.6.

Book: [Generic Data Types](https://doc.rust-lang.org/book/ch10-01-syntax.html)
and [Traits as Parameters](https://doc.rust-lang.org/book/ch10-02-traits.html#traits-as-parameters).

### Capabilities: a value as proof

```rust,ignore
pub struct ClinicalAccess {
    practitioner: PractitionerId,
}

pub struct ScheduleAccess {
    _private: (),
}
```

The fields are private, so other crates can't write
`ClinicalAccess { .. }`. The `compile_fail` doctest proves it. The only
way to get one is `grant`. In step 1.8, functions that touch clinical notes
will take a `&ClinicalAccess`:

```rust,ignore
fn read(note: &ClinicalNote, access: &ClinicalAccess) -> ...
```

Then forgetting the check is a compile error, not a bug found in review.
`ScheduleAccess` and `AuditAccess` hold no data. `_private: ()` is a private
field of size zero that exists only to block outside construction.

Book: [Defining an Enum](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)
(variants with data) and
[Encapsulation](https://doc.rust-lang.org/book/ch18-01-what-is-oo.html#encapsulation-that-hides-implementation-details).

### Exhaustive `match` instead of `_`

```rust,ignore
match role {
    Role::Administrator => Some(Self { _private: () }),
    Role::Practitioner(_) | Role::Receptionist => None,
}
```

Each `grant` lists every role, even the denied ones. If a new role is added
later, every `grant` stops compiling until someone decides what that role
may access. A `_ => None` arm would deny it silently, which is safe, but
nobody would have made the decision.

Book: [The `match` Control Flow Construct](https://doc.rust-lang.org/book/ch06-02-match.html#matches-are-exhaustive).

## Design choices worth questioning

- **Capability tokens instead of `role.can(Permission) -> bool`.** A
  boolean check is simpler, but nothing makes the caller use it. A token
  makes the check part of the function's signature.
- **The trait isn't sealed.** Another crate can implement `Capability` for
  its own types. It still can't build `ClinicalAccess`, so the clinical
  rule holds. Sealing (a private supertrait) would keep the list of
  capabilities closed, and costs one more concept.
- **Tokens are `Copy`.** Copying a token doesn't grant anything new: you
  needed one to copy it. They don't expire, though. Inside one request
  that's fine, but tokens shouldn't be stored for later use.
- **`Role` is trusted.** Anyone can write `Role::Receptionist`. Turning a
  logged-in user into a `Role` belongs to M4, outside the domain.
- **One role per person.** A practitioner who also runs the clinic would
  need two roles. A set of roles can come later if the domain needs it.
- **The administrator isn't a superuser.** It gets audit access but no
  clinical access, as the README requires.
- **`ScheduleAccess` and `AuditAccess` have no users yet.** They are here so
  the trait has more than one implementation, and so the access table is
  complete. Gating `Schedule::book` waits until M2/M4 has a caller.
- **`AccessDenied` doesn't name the role.** Its message says which
  capability was refused. The caller already knows the role.

## Tests

Every role is checked against every capability: only practitioners get
`ClinicalAccess`, every role gets `ScheduleAccess`, and only administrators
get `AuditAccess`. `ClinicalAccess` carries the practitioner's id. Calling
`Capability::grant` directly gives the same answer as `Role::grant`. A
refusal names the capability, has a readable message and implements
`Error`. A `compile_fail` doctest proves `ClinicalAccess` can't be built
with a struct literal.
