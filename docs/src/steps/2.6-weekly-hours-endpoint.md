# 2.6 Setting weekly hours over HTTP

## Goal

Let a client set a practitioner's hours the way step 2.3 lets the code
describe them: a week of local times in a time zone. Until now, the only
practitioner with hours was the one in the server's seed. This step adds
`PUT /practitioners/{id}/hours`, which takes a time zone name, a start date
and a weekly template, expands it over four weeks with
`WeeklyHours::working_hours`, and puts the result in the practitioner's
schedule.

Two decisions shape it:

- **The client sends `from`**, the first local date the hours apply to.
  The server has no clock, so the same body always gives the same result.
- **Hours change from `from` on.** Shifts before the start of `from` are
  kept, and so are their appointments. If a booked appointment wouldn't fit
  the new hours, the whole request is refused and nothing changes.

Roadmap row: *Endpoint to set a practitioner's weekly hours: a time zone
name parsed to a `Tz`, expanded over a fixed horizon into their schedule*.
Concepts: parsing at the edge, path extractors, `PUT` semantics.

## Rust concepts

### Parsing at the edge: `FromStr` and `map_err`

```rust,ignore
let time_zone: Tz = body
    .time_zone
    .parse()
    .map_err(|_| ApiError::InvalidTimeZone {
        name: body.time_zone.clone(),
    })?;
```

`str::parse` works for any type that implements the standard `FromStr`
trait, and chrono-tz implements it for `Tz` by looking the name up in its
table of IANA zones. The type annotation on `time_zone` is what tells
`parse` which `FromStr` to call.

The body keeps the zone as a `String`, and the handler turns it into a
`Tz` before anything else sees it. From there on, `WeeklyHours::new` and
the use case take a `Tz`, which is always a real zone, so no code past the
handler checks a name. That's "parsing at the edge": the delivery layer
turns text into types, and the inner layers never get text they would have
to validate. The same idea is behind every newtype in the domain, such as
`Email`.

chrono-tz's error type says only that the name is unknown, so `map_err`
replaces it with an `ApiError` that has its own code and repeats the name.

Book: [Creating Custom Types for Validation](https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html#creating-custom-types-for-validation).

### serde reads chrono's types through `FromStr` too

```rust,ignore
#[derive(Debug, Clone, Copy, PartialEq, Eq, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct WeeklyShiftBody {
    pub weekday: Weekday,
    pub start: NaiveTime,
    pub end: NaiveTime,
}
```

With chrono's `serde` feature (on since step 2.4), `NaiveDate`,
`NaiveTime` and `Weekday` deserialize from strings by calling their own
`FromStr`. That's why `"09:00"` works without seconds, and `"monday"` or
`"MON"` work as well as `"Mon"`. A value that doesn't parse fails the whole
body, and axum answers 422 `invalid_body` as for any mistyped field.

The time zone could have been read the same way, with chrono-tz's `serde`
feature. Parsing it by hand gives it its own error code,
`invalid_time_zone`, which a client can show next to the field.

`deny_unknown_fields` applies to each struct separately, so it's on both
the body and each shift.

### Collecting into a `Result`

```rust,ignore
let shifts = body
    .shifts
    .iter()
    .map(|shift| WeeklyShift::new(shift.weekday, shift.start, shift.end))
    .collect::<Result<Vec<_>, _>>()?;
```

`map` gives an iterator of `Result<WeeklyShift, WeeklyHoursError>`.
`collect` can build a `Result<Vec<WeeklyShift>, WeeklyHoursError>` from
it: `Ok` with every value if all are `Ok`, or the first `Err`, and it stops
at that first error. The `?` then returns it, and `#[from]` turns it into
`ApiError::WeeklyHours`. It works because `Result` implements
`FromIterator` whenever its `Ok` type does.

Docs: [`impl FromIterator for Result`](https://doc.rust-lang.org/std/result/enum.Result.html#impl-FromIterator%3CResult%3CA,+E%3E%3E-for-Result%3CV,+E%3E).

### `PUT` and choosing the status from the result

```rust,ignore
let status = match set.outcome {
    HoursOutcome::Created => StatusCode::CREATED,
    HoursOutcome::Replaced => StatusCode::OK,
};
Ok((status, Json(HoursBody { .. })))
```

`PUT` means "make the resource at this URL what the body says". Sending it
twice must leave the same state as sending it once, which is called being
idempotent, so a client that lost the answer can safely retry. HTTP asks
for `201 Created` when a `PUT` creates the resource and `200 OK` when it
replaces it.

The use case doesn't know about HTTP, so it reports what happened as an
enum, `HoursOutcome`, and the handler maps that to a status. The handler
returns a tuple, `(StatusCode, Json<_>)`, because axum implements
`IntoResponse` for it, as `book` already does with a fixed `CREATED`.

`Path<u64>` is the same extractor as the agenda's. The route
`/practitioners/{id}/hours` has the same `{id}`, and a bad one gives the
same 400 `invalid_path`.

### Checked date arithmetic, and why a panic is worse here

```rust,ignore
let until = from
    .checked_add_days(Days::new(HORIZON_DAYS))
    .ok_or(SetHoursError::OutOfRange)?;
```

chrono's dates end at year 262142. `from + 28 days` can pass that, and the
`+` operator would panic; `checked_add_days` returns `None` instead. The
use case also checks two days of margin on either side, because reading a
local time near a daylight saving change looks one day either side of it
(step 2.3's `gap_end`), and that uses `+` and `-`.

A panic in a handler is worse than a crash here. axum would drop that
connection and keep serving, but if the panic happens while the storage
`Mutex` is locked, the mutex is *poisoned*, and every later request gets
500 from `AppState::lock`. One bad date would break the server until it
restarts. The tests try `from` at the first and last dates the check
allows, in the zones with the largest offsets, and at `NaiveDate::MIN` and
`MAX`.

Book: [Unrecoverable Errors with `panic!`](https://doc.rust-lang.org/book/ch09-01-unrecoverable-errors-with-panic.html),
and [Using Mutexes](https://doc.rust-lang.org/book/ch16-03-shared-state.html).

### Struct update syntax in tests

```rust,ignore
SetHoursRequest {
    clinic: ClinicId::new(2),
    ..request(mondays(14, 18), date(2026, 3, 30))
}
```

`..other` fills every field not written out from `other`. Here it reuses
the usual request with a different clinic. `other` is moved, so any field
taken from it that isn't `Copy`, such as `hours`, can't be used from
`other` afterwards.

Book: [Creating Instances from Other Instances with Struct Update Syntax](https://doc.rust-lang.org/book/ch05-01-defining-structs.html#creating-instances-from-other-instances-with-struct-update-syntax).

## Design choices worth questioning

- **`from` is in the body, not taken from a clock.** That keeps the domain
  and `app` without a clock, makes the same body give the same result, and
  keeps the walkthrough stable. The cost is that a client can set hours for
  any date, past ones included. A `Clock` port would allow "from today",
  but tests would then need a fixed clock.
- **Hours change from the start of `from`, in the new time zone.** Earlier
  shifts are kept, so changing next month's hours doesn't erase last
  week's, or strand its appointments. If the old hours were in another
  zone, a shift may straddle that instant; it's cut short there.
- **The horizon is fixed at 28 days.** Long enough to book a month ahead,
  short enough that a tzdata update reaches new shifts soon. Nothing extends
  the hours when the horizon runs out: the client sends them again. A job
  that re-expands stored templates would need the template stored, which
  this step doesn't do.
- **Only the UTC expansion is stored**, not the weekly template. So there's
  no `GET` for the hours yet, and the answer to the `PUT` is the only place
  the expansion is shown. Storing the template is a natural follow-up,
  probably with the database in M3.
- **Appointments past the new horizon block the change.** A `PUT` with an
  earlier `from` ends its horizon earlier too, and an appointment booked
  under the old hours after that end no longer fits. Refusing is safe;
  keeping old shifts after the horizon would be the alternative.
- **A `PUT` creates a schedule for any practitioner ID.** There is no
  practitioner registry, so a schedule is what makes a practitioner exist.
  Any clinic can create any ID for itself, and IDs are per clinic, so this
  doesn't cross clinics. M3/M4 bring real practitioner records.
- **409 for a stranded appointment, 422 for bad input.** The body is valid;
  it clashes with the current state, like a double booking. That's what
  409 means, and it matches `overlaps`.
- **Time zone names are matched exactly.** chrono-tz's `case-insensitive`
  feature would add `Tz::from_str_insensitive`, but IANA names are
  case-sensitive, and one more feature means a bigger build. The answer
  echoes `Tz::name`, a `&'static str`, so `HoursBody` holds no copy.
- **The seed still gives practitioner 1 its hours.** Setting them through
  the API would mean opening the walkthrough with a `PUT`, and every
  earlier transcript line would move. The walkthrough adds practitioner 2
  instead.

## Tests

`crates/domain/tests/working_hours.rs`: `replace_from` keeps shifts before
the cut and takes the replacement's after it; drops replacement shifts
before the cut; cuts short a shift of either side that straddles the cut,
and merges two that meet there; and handles empty hours on either side.

`crates/domain/tests/schedule.rs`: `hours` returns the working hours;
`replace_hours` keeps appointments that still fit, makes later bookings use
the new hours, refuses hours that leave an appointment outside (naming the
earliest) or fit it only across two shifts, and leaves the schedule
unchanged when it refuses.

`crates/app/tests/weekly_hours.rs`: `day_start` is local midnight, or the
jump when midnight is skipped (Santiago, 2026-09-06).

`crates/app/tests/hours.rs`: a first call creates the schedule; the
horizon is 28 days, expanded across Santiago's DST change; a second call
answers `Replaced`, keeps earlier shifts and appointments, and returns only
the new shifts; the same call twice leaves the same schedule; a stranded
appointment is refused and nothing is saved, including one past the new
horizon; a skipped midnight cuts the old hours at the jump; `NaiveDate::MIN`
and `MAX` give `OutOfRange` and save nothing, while the nearest accepted
dates expand without panicking in Santiago, Kiritimati (+14:00) and
`Etc/GMT+12`; and each clinic sets its own practitioner's hours.

`crates/api/tests/hours.rs`: 201 with the exact JSON shape, then 200 with
the same body; the new hours take bookings; earlier shifts and their
appointments are kept; a stranded appointment is 409
`appointment_outside_hours`; no shifts is allowed; weekday names in any case
and in full; an unknown or wrongly cased zone is 422 `invalid_time_zone`; a
shift that doesn't end after it starts and overlapping shifts are 422 with
their own codes; a `from` near the end of the calendar is 422
`out_of_range`; malformed, missing and unknown fields are 422
`invalid_body`; a bad `{id}` is 400; a missing clinic header is 400; and
hours set at clinic 2 don't touch clinic 1.

```sh

```

Then the walkthrough from [step 2.5](2.5-serving-http.md#see-it-run),
followed by the `[2.6]` requests below, against a fresh server. They give
practitioner 2 at clinic 1 hours on Mondays in Santiago, across the night
of 2026-04-04 when Santiago's clocks go back from -03:00 to -04:00, so
