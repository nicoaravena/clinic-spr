# 3.1 Async, fallible ports

## Goal

Get the ports ready for a database before there is one. Postgres is
reached over the network: sqlx's calls are `async`, and every one of them
can fail. Until now the ports were synchronous and couldn't fail:
`get` returned an `Option<Schedule>` and `save` returned nothing. This step
changes only their shape. Every port method becomes `async` and returns a
`Result<_, StorageError>`, and the in-memory adapters, the use cases, the
handlers and the server follow.

Nothing a client can see changes. The walkthrough's transcript is the same
byte for byte. The in-memory adapters never fail, so the new 500 answer can
only be seen in tests, with adapters written to fail.

Roadmap row: *Ports become `async` and fallible (`StorageError`, mapped to
500); in-memory adapters and handlers follow. No behavior change*.
Concepts: `async fn` in traits, `Send` bounds on returned futures,
`tokio::sync::Mutex` vs `std`.

## What changed

- `crates/app` (see [app](../reference/app.md)):
  - `ports.rs`: `get`, `save` and `find` return
    `impl Future<Output = Result<_, StorageError>> + Send`. New:
    `StorageError` with `StorageError::new`. A `compile_fail` doctest shows
    that the ports can't be trait objects any more.
  - `in_memory.rs`: the adapters implement the ports with `async fn` and
    always return `Ok`.
  - `booking.rs`, `agenda.rs`, `hours.rs`: the use cases are `async fn`,
    lose their `?Sized` bounds, and their errors gain
    `Storage(StorageError)` and lose `Clone`, `Copy`, `PartialEq` and `Eq`.
  - New dev-dependency: `tokio` (`macros`, `rt`) for `#[tokio::test]`,
    already in `Cargo.lock`.
- `crates/api` (see [api](../reference/api.md)):
  - `state.rs`: `AppState<S, T>` is generic over the adapters and keeps them
    behind a `tokio::sync::Mutex`. `lock` is `async` and can't fail.
  - `lib.rs`, `appointments.rs`, `practitioners.rs`: `router` and the
    handlers take the same `S` and `T`, and `.await` the use cases.
  - `error.rs`: `ApiError::Internal` is gone. Each `Storage` variant is 500
    `internal`. Every 5xx answers the message `internal server error` and
    logs the cause to stderr.
  - `tokio` (`sync`) becomes a normal dependency; it was a dev-dependency.
- `crates/clinic`: `seed::demo_state` is `async` and saves through the
  port; `main` awaits it.
- Tests: `crates/app/tests/storage_errors.rs` (new, 9 cases) and
  `crates/api/tests/storage_errors.rs` (new, 4 cases). The existing app and
  api tests are `async`. The app's two trait-object tests are replaced by
  tests that the use cases' futures are `Send`, and the api's status table
  swaps `Internal` for the three `Storage` variants.

## Rust concepts

### `async fn` in a trait, with a `Send` bound

```rust,ignore
pub trait ScheduleRepository {
    fn get(
        &self,
        clinic: ClinicId,
        practitioner: PractitionerId,
    ) -> impl Future<Output = Result<Option<Schedule>, StorageError>> + Send;
    // ...
}
```

An `async fn` is a function that returns a future. Since Rust 1.75 a trait
can declare one, and the trait above could have said
`async fn get(&self, ..) -> Result<..>`. Rust warns about that in a public
trait (the `async_fn_in_trait` lint), and for a good reason: the future's
type is chosen by each implementation, so the trait would promise nothing
about it, and a caller couldn't require it to be `Send`.

axum needs it to be `Send`. Its runtime has several threads, and a handler
that pauses at an `.await` may resume on another thread, so the handler's
future must be allowed to move between threads. That future contains the
port's future while it waits on it, so the port's future must be `Send` too.

Writing the desugared form, `-> impl Future<Output = ..> + Send`, makes it
part of the contract. Implementations don't have to write it that way:

```rust,ignore
impl ScheduleRepository for InMemorySchedules {
    async fn get(
        &self,
        clinic: ClinicId,
        practitioner: PractitionerId,
    ) -> Result<Option<Schedule>, StorageError> {
        Ok(self.schedules.get(&(clinic, practitioner)).cloned())
    }
    // ...
}
```

The compiler checks that this `async fn`'s future is `Send`. Here it is
because it only holds `&InMemorySchedules`, and a `HashMap` of schedules
is `Sync`.

The in-memory `get` never waits on anything, so its future is ready the
first time it's polled. Being `async` costs it almost nothing, and lets it
stand in for a database adapter.

Book: [Fundamentals of Asynchronous Programming](https://doc.rust-lang.org/book/ch17-00-async-await.html),
and the Rust blog's
[Announcing `async fn` and return-position `impl Trait` in traits](https://blog.rust-lang.org/2023/12/21/async-fn-rpit-in-traits.html).

### Why the ports stopped being trait objects

```rust,ignore
// Before: the router's state held the adapters as trait objects.
pub(crate) struct Store {
    pub(crate) schedules: Box<dyn ScheduleRepository + Send>,
    pub(crate) types: Box<dyn AppointmentTypes + Send>,
}
```

A trait object calls methods through a table of function pointers, and
every entry must have one signature for every implementation. A method
returning `impl Future` returns a different type, of a different size, for
each implementation, so no single entry fits. The trait isn't *dyn
compatible*, and `Box<dyn ScheduleRepository>` no longer compiles. The
`ports` module has a `compile_fail` doctest that shows it (error E0038).

So the api crate is generic instead:

```rust,ignore
pub struct AppState<S, T> {
    store: Arc<Mutex<Store<S, T>>>,
}

pub fn router<S, T>(state: AppState<S, T>) -> Router
where
    S: ScheduleRepository + Send + Sync + 'static,
    T: AppointmentTypes + Send + Sync + 'static,
{
    Router::new()
        .route("/appointments", post(appointments::book::<S, T>))
        // ...
}
```

The `clinic` binary is the only place that names the types,
`AppState<InMemorySchedules, InMemoryAppointmentTypes>`. A generic
function isn't a value until its type parameters are known, which is why
each handler is written `book::<S, T>` when it's given to `post`. The
bounds read as: each adapter can move to another thread (`Send`), be
shared between threads (`Sync`, because one request holds `&T` while
awaiting), and borrows nothing (`'static`).

`#[derive(Clone)]` on `AppState<S, T>` would require `S: Clone` and
`T: Clone`, though only the `Arc` is cloned, so `Clone` is written by hand.
The use cases lost their `?Sized` bounds, whose only purpose was to accept
`dyn ScheduleRepository`.

The `async-trait` crate is the other way out: it rewrites each method to
return `Pin<Box<dyn Future + Send>>`, which is dyn compatible at the cost
of one allocation per call. Step 3.2 replaces the ports with tenant
sessions that have associated types, which aren't trait objects either, so
generics are where this was heading anyway.

Book: [Using Trait Objects to Abstract over Shared Behavior](https://doc.rust-lang.org/book/ch18-02-trait-objects.html),
and the Reference on
[dyn compatibility](https://doc.rust-lang.org/reference/items/traits.html#dyn-compatibility).

### `tokio::sync::Mutex` instead of `std::sync::Mutex`

```rust,ignore
let mut store = state.lock().await;
let store = &mut *store;
let appointment =
    book_appointment(&mut store.schedules, &store.types, &access, request).await?;
```

The lock must be held from reading the schedule to saving it, or two
requests could both see the same slot free. Until now nothing in between
`.await`ed. Now `book_appointment` does, three times.

A `std::sync::MutexGuard` isn't `Send`: some platforms require a lock to be
released by the thread that took it. A future holding one across an
`.await` isn't `Send` either, and axum refuses the handler, with a long
error that ends in "future cannot be sent between threads safely". Even
where that compiled, a thread blocked on a std lock can't run other tasks,
and the task holding the lock may be waiting to run on that very thread.

tokio's `Mutex` is locked with `.lock().await`. A task that has to wait
gives its thread back to the runtime. Its guard is `Send`, so it can be
held across an `.await`. It's slower than the std one, which is why tokio's
docs recommend std's whenever the lock isn't held across an `.await`.

tokio's mutex isn't poisoned by a panic. Step 2.6 relied on poisoning: a
panic while holding the lock made every later request a 500, because the
storage might be half-changed. Now `lock` can't fail, and
`ApiError::Internal` went with the poisoned lock. The in-memory adapters
change the store in one step (`HashMap::insert`), so a panic can't leave it
half-changed; the database adapters will use transactions instead.

Book: [Using Mutexes to Allow Access to Data from One Thread at a Time](https://doc.rust-lang.org/book/ch16-03-shared-state.html),
and tokio's notes on
[which kind of mutex to use](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html#which-kind-of-mutex-should-you-use).

### A future borrows its arguments until it's awaited

```rust,ignore
// Doesn't compile: `access()` is a temporary dropped at the end of the statement.
let booking = book_appointment(&mut schedules, &types, &access(), request(at(9, 0)));
assert!(assert_send(booking).await.is_ok());

// Compiles: `access` lives until the end of the test.
let access = access();
let booking = book_appointment(&mut schedules, &types, &access, request(at(9, 0)));
```

Calling an `async fn` runs none of its body. It packs the arguments into a
future, and that future keeps every reference it was given until it
finishes. Written as `book_appointment(.., &access(), ..).await`, in one
statement, the temporary lives long enough. Keeping the future in a
variable, as the `Send` test does, keeps the borrow alive past the
statement, and the compiler says so (E0716). The same rule is why the
agenda handler can take the lock as a temporary,
`&state.lock().await.schedules`: the guard lives to the end of the
statement, after the use case's `.await`.

### An error with a source, and what it costs

```rust,ignore
#[derive(Debug, Error)]
#[error("storage failed")]
pub struct StorageError {
    #[source]
    source: Box<dyn Error + Send + Sync>,
}

impl StorageError {
    pub fn new(source: impl Into<Box<dyn Error + Send + Sync>>) -> Self { .. }
}
```

`StorageError` says only that storage failed. Why it failed is its
`source()`, the error it was built from. `Into<Box<dyn Error + Send +
Sync>>` is implemented for every such error and for `&str` and `String`,
so `StorageError::new` takes an sqlx error in a later step and a plain
message in a test double. `Send + Sync` lets it cross threads, and inside
an `ApiError` it does.

Each use case wraps it with `#[error(transparent)]`, which passes the
message and the source on unchanged:

```rust,ignore
pub enum BookAppointmentError {
    // ...
    #[error(transparent)]
    Storage(#[from] StorageError),
}
```

The cost: `Box<dyn Error>` isn't `Clone`, `Copy` or `PartialEq`, so neither
are the use case errors. Tests that compared errors with `assert_eq!` now
use `matches!`, with a match guard where the error carries a value:

```rust,ignore
assert!(
    matches!(
        result,
        Err(BookAppointmentError::Booking(BookingError::Overlaps { existing }))
            if existing == slot(at(9, 0), at(9, 30))
    ),
    "{result:?}"
);
```

Book: [Recoverable Errors with `Result`](https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html),
and [Patterns and Matching: Extra Conditionals with Match Guards](https://doc.rust-lang.org/book/ch19-03-pattern-syntax.html#extra-conditionals-with-match-guards).

### 500s: a fixed message for the client, the cause for the logs

```rust,ignore
let status = self.status();
let message = if status.is_server_error() {
    eprintln!("clinic-api: {status}: {}", error_chain(&self));
    "internal server error".to_owned()
} else {
    self.to_string()
};
```

A storage error's cause can name a host, a table or a constraint, which a
client has no use for and an attacker might. So every 5xx answers the same
body, `{"error":"internal","message":"internal server error"}`, and the
cause goes to stderr as one line, the error followed by each of its
sources:

```text
clinic-api: 500 Internal Server Error: storage failed: connection refused by db.internal:5432
```

`ApiError::status` and `code` match each use case error without a
wildcard, so adding `Storage` didn't compile until it had a status and a
code. That's the reason they're matched variant by variant.

## Design choices worth questioning

- **Generic state instead of `async-trait`.** Generics keep the ports free
  of boxing and of a macro, and are where step 3.2's sessions lead. The
  cost is type parameters on `AppState`, `router` and every handler, and
  longer compiler errors when a bound is missing.
- **One opaque `StorageError` for everything.** A use case can't tell a
  lost connection from a full disk, and doesn't need to yet: all of them
  are 500. A unique-key violation that should be a 409 will need its own
  variant, and step 3.6's overlap guard is the first.
- **Use case errors gave up `PartialEq`.** A `StorageError` that kept only
  a message would have kept it, but would throw away the driver error and
  its chain, which is what the logs need.
- **`eprintln!` from the api crate.** It's the edge, and stderr is where the
  binary already logs. Structured logs with request IDs are M8's job.
- **Any 5xx hides its message,** not only storage errors. `InvalidPath`
  can also be a 500 when a route and its handler disagree, which is a bug
  in this crate; its message now goes to stderr too.
- **One lock still serializes every request.** It's what keeps
  read-book-save atomic, now across `.await`s. Step 3.2 gives each request
  its own unit of work, and Postgres transactions take over in 3.4.
- **Seeding goes through the async port** rather than a synchronous
  `InMemorySchedules::insert`. It costs `app().await` in 37 api tests, but
  the in-memory adapters keep the API they had.

## Tests

`crates/app/tests/storage_errors.rs`: with an adapter that can't be reached,
booking (failing schedules or failing appointment types), the agenda and
setting hours each return their `Storage` variant; with an adapter whose
`save` fails, a booking and new hours are errors, not successes, and the
booking isn't stored; `StorageError`'s message is "storage failed" and its
source is the cause; a use case error passes both on; and `StorageError` is
`Send + Sync + 'static`.

`crates/app/tests/booking.rs` and `agenda.rs`: the use cases' futures are
`Send`, replacing the tests that called them through trait objects. The
other app tests are the same cases, `async`.

`crates/app/src/ports.rs`: a `compile_fail` doctest boxing
`InMemorySchedules` as `dyn ScheduleRepository` fails with E0038.

`crates/api/tests/storage_errors.rs`: with storage that can't be reached,
`POST /appointments`, `GET /practitioners/{id}/agenda` and
`PUT /practitioners/{id}/hours` all answer 500 with the fixed body and
nothing of the cause; a request without `X-Clinic-Id` is still a 400,
refused before storage is touched.

`crates/api/tests/appointments.rs`: the status and code table has the
three `Storage` variants as 500 `internal`, and `AppState` with the
in-memory adapters is still `Clone + Send + Sync + 'static`.

The walkthrough runs unchanged against `expected-output.txt`.
