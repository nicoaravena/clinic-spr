# 2.1 The app crate and ports

## Goal

Book an appointment the way the server will: look up a practitioner's
schedule and the clinic's appointment types in storage, let the domain
decide, and save the result. Storage is reached only through traits, so the
same use case will run on Postgres in M3. This step opens M2.

Roadmap row: *`app` crate: `ScheduleRepository` and `AppointmentTypes`
ports, in-memory adapters, `book_appointment` use case; appointments record
their patient*. Concepts: traits as ports, generics vs `dyn`, `#[from]`
error wrapping, `HashMap`.

## What changed

- `crates/app`: a new library crate, `clinic-app`. See
  [app](../reference/app.md).
  - `src/ports.rs`: `ScheduleRepository` and `AppointmentTypes`.
  - `src/in_memory.rs`: `InMemorySchedules`, `InMemoryAppointmentTypes`,
    `DuplicateAppointmentType`.
  - `src/booking.rs`: `book_appointment`, `BookingRequest`,
    `BookAppointmentError`.
  - `tests/booking.rs` and `tests/in_memory.rs`.
- `crates/domain`: an `Appointment` now records its patient.
  `Schedule::book` takes a `PatientId` first, and `Appointment::patient`
  returns it. See [schedule](../reference/schedule.md) and
  [appointment](../reference/appointment.md).
- `crates/clinic`: depends on `clinic-app`, and adds the `[2.1]` part of
  the day.
- `docs/ROADMAP.md`: M2 split into steps 2.1 to 2.5. The two decisions made
  before this step are recorded there: ports are sync until M3, and the
  clinic comes from an `X-Clinic-Id` header until M4.

## Rust concepts

### Traits as ports

```rust,ignore
pub trait ScheduleRepository {
    fn get(&self, clinic: ClinicId, practitioner: PractitionerId) -> Option<Schedule>;
    fn save(&mut self, clinic: ClinicId, practitioner: PractitionerId, schedule: Schedule);
}
```

In step 1.7, a trait (`Capability`) described a family of types the domain
owns. Here a trait describes a *need*: the use case needs to get and save
schedules, and doesn't care how. That's a *port*. A type that implements
it, such as `InMemorySchedules`, is an *adapter*. In M3 a Postgres adapter
implements the same trait, and `book_appointment` doesn't change.

The trait lives in `app`, next to the code that uses it, not next to the
code that implements it. That's what keeps the arrows pointing inward:
`db` will depend on `app` to see the trait, and `app` never depends on
`db`.

Every method takes the `ClinicId` first. This is the in-memory version of
M3's `TenantTx`: storage can't be reached without naming a tenant.

Book: [Defining Shared Behavior with Traits](https://doc.rust-lang.org/book/ch10-02-traits.html).

### Generics vs `dyn`

```rust,ignore
pub fn book_appointment<S, T>(
    schedules: &mut S,
    types: &T,
    _access: &ScheduleAccess,
    request: BookingRequest<'_>,
) -> Result<Appointment, BookAppointmentError>
where
    S: ScheduleRepository + ?Sized,
    T: AppointmentTypes + ?Sized,
```

There are two ways to accept "anything that implements a trait":

- **Generics** (`S: ScheduleRepository`). The compiler makes one copy of
  the function for each concrete type it's called with
  (*monomorphization*). Calls are direct and can be inlined, but each copy
  adds to the binary size.
- **Trait objects** (`&mut dyn ScheduleRepository`). One copy of the
  function, and each call goes through a table of function pointers (a
  *vtable*) looked up at runtime.

`?Sized` lets the caller choose. A type parameter is normally assumed to be
`Sized`, meaning its size is known at compile time. `dyn ScheduleRepository`
isn't `Sized`, because it could be any implementor. With `?Sized`, `S` may be
`dyn ScheduleRepository`, and the test `works_through_trait_objects` does
exactly that:

```rust,ignore
let schedules: &mut dyn ScheduleRepository = &mut schedules;
let types: &dyn AppointmentTypes = &types;
book_appointment(schedules, types, &access(), request(at(9, 0)))
```

Without `?Sized` that call doesn't compile. The parameters are references
(`&mut S`), so the function never needs to know `S`'s size anyway.

Book: [Using Trait Objects](https://doc.rust-lang.org/book/ch18-02-trait-objects.html)
and [Generic Data Types](https://doc.rust-lang.org/book/ch10-01-syntax.html#performance-of-code-using-generics).
Reference: [`Sized`](https://doc.rust-lang.org/std/marker/trait.Sized.html).

### Wrapping an error with `#[from]`

```rust,ignore
pub enum BookAppointmentError {
    #[error("clinic has no schedule for that practitioner")]
    UnknownPractitioner,
    #[error("clinic has no appointment type with that name")]
    UnknownAppointmentType,
    #[error(transparent)]
    Booking(#[from] BookingError),
}
```

The use case can fail in its own ways (nothing found) and in the domain's
ways (overlap, outside working hours). `#[from]` makes `thiserror` write
`impl From<BookingError> for BookAppointmentError`, so `?` converts the
domain error on the way out:

```rust,ignore
let appointment = schedule
    .book(request.patient, request.start, appointment_type)?
    .clone();
```

`#[error(transparent)]` reuses the inner error's message, so callers print
"appointment overlaps an existing appointment" without a wrapper around it.
The variant still holds the full `BookingError`, so step 2.4 can `match` on
it to choose an HTTP status code.

Docs: [`thiserror`](https://docs.rs/thiserror/2).

### Clone before you move

```rust,ignore
let appointment = schedule.book(/* ... */)?.clone();
schedules.save(request.clinic, request.practitioner, schedule);
Ok(appointment)
```

`book` returns `&Appointment`, a reference into `schedule`. `save` takes
`schedule` by value, which moves it into the repository. A reference into
it can't outlive the move, so the appointment is cloned first. Cloning
after the move instead, with `Ok(appointment.clone())`, is refused with
`E0505` (*cannot move out of `schedule` because it is borrowed*).

Book: [What is Ownership?](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html).

### `HashMap` with a tuple key, and `entry`

```rust,ignore
schedules: HashMap<(ClinicId, PractitionerId), Schedule>,
```

A tuple implements `Hash` and `Eq` when every part does, and both ID types
derive them (step 1.2). So the pair can be a key, and the clinic is part of
every lookup.

`InMemoryAppointmentTypes::add` uses the entry API:

```rust,ignore
let offered = self.types.entry(clinic).or_default();
```

`entry` finds the slot for `clinic`, and `or_default` puts an empty `Vec`
there if there's nothing yet. One lookup, and the result is a `&mut Vec`
to push to.

Book: [Storing Keys with Associated Values in Hash Maps](https://doc.rust-lang.org/book/ch08-03-hash-maps.html).

### Struct update syntax in tests

```rust,ignore
let request = BookingRequest {
    practitioner: PractitionerId::new(2),
    ..request(at(9, 0))
};
```

`..other` fills every field not written from another value. Each test
changes only the field it is about.

Book: [Creating Instances from Other Instances](https://doc.rust-lang.org/book/ch05-01-defining-structs.html#creating-instances-from-other-instances-with-struct-update-syntax).

## Design choices worth questioning

- **Sync ports.** The ports are plain `fn`s for now, so this step needs no
  async runtime. M3's sqlx adapter is async, so the trait signatures will
  change across `app` and `api` then. That cost was accepted so async
  arrives with HTTP in 2.4, where it's needed, and not before.
- **`get` returns a copy.** The use case gets an owned `Schedule`, changes
  it, and saves it back. That's simple and keeps the adapter's data private,
  but it copies every appointment the practitioner ever had. A database
  adapter will load a date range instead. Two bookings at once would also
  race between `get` and `save`. That's not possible yet, since `save` needs
  `&mut`, but it becomes possible with a shared server in 2.4. M3's
  exclusion constraint is the real guard.
- **Practitioner checked before type.** "Who" before "what". It also means
  a clinic asking about another clinic's practitioner is told the
  practitioner is unknown, whatever else is wrong with the request.
- **Unknown practitioner means "no schedule".** There's no practitioner
  registry yet. A practitioner exists for booking purposes when they have a
  schedule at that clinic.
- **Types are found by exact name.** No trimming, no case folding. An ID
  will replace the name when there's a database to generate one. Until
  then, the API in 2.4 has to send the exact name.
- **Uniqueness lives in the adapter.** "Names are unique within a clinic" is
  checked by `InMemoryAppointmentTypes::add`, not by a domain type. In M3 a
  unique index will enforce it. One could argue for a domain
  `AppointmentTypeCatalog` that owns the rule instead.
- **The access token is unused.** As with clinical notes, `_access` makes
  the call impossible without the check. Any role gets `ScheduleAccess`
  today, so it rules nothing out yet.
- **Adapters live in `app`.** The in-memory adapters are in `app::in_memory`
  rather than their own crate. They have no dependencies, tests use them,
  and the M2 server will too. A separate crate would be more consistent
  with `db`, at the cost of one more crate.
- **Patient on the appointment, in the domain.** This changes
  `Schedule::book`'s signature from M1. The alternative, keeping the patient
  only in `app`, would split an appointment's data across two layers.
- **No appointment ID yet.** Nothing refers to one booking until
  cancellation or rescheduling exists.

## Tests

`tests/in_memory.rs`: a saved schedule reads back, and saving again replaces
it. A schedule or appointment type saved for clinic 1 is invisible to
clinic 2, even under the same practitioner ID. A duplicate type name in one
clinic is refused and keeps the first type, and the same name in another
clinic is allowed.

`tests/booking.rs`: a booking returns the scheduled appointment with its
patient, type and slot, and the stored schedule contains it. An unknown
practitioner, an unknown type and another clinic's practitioner are
refused, practitioner first. The domain's overlap refusal comes through as
`Booking(Overlaps)`. A refused booking leaves the stored schedule unchanged.
The use case accepts trait objects. Errors have readable messages, and a
domain refusal keeps the domain's message.

`crates/domain/tests/schedule.rs`: every booking now names a patient, and
the appointment records it.

A `compile_fail` doctest proves `InMemoryAppointmentTypes`'s fields are
private, so `add` can't be bypassed.
