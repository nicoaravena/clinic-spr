# 1.8 Clinical notes

## Goal

Let practitioners write notes about a patient, and correct them without
losing what was there before. Only practitioners can reach a note's
content, and only its author can correct it. This step closes M1.

Roadmap row: *`ClinicalNote` that keeps versions on correction*. Concepts:
lifetimes, immutability by design.

## Rust concepts

### Immutability by design

```rust,ignore
pub struct ClinicalNote {
    patient: PatientId,
    original: NoteVersion,
    corrections: Vec<NoteVersion>,
}
```

Rust values can be changed only through a `&mut` or by their owner. The
fields are private, and the only method that takes `&mut self` is
`correct`, which pushes onto `corrections`. Nothing hands out a
`&mut NoteVersion`, and `NoteVersion` has no setters. So "a version never
changes" isn't a convention to remember: there is no code that could
change one.

Splitting `original` from `corrections` makes "a note always has a
version" part of the type. `current` doesn't need an `unwrap`:

```rust,ignore
self.corrections.last().unwrap_or(&self.original)
```

Book: [Variables and Mutability](https://doc.rust-lang.org/book/ch03-01-variables-and-mutability.html)
and [References and Borrowing](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html).

### Lifetime elision

```rust,ignore
pub fn current(&self, _access: &ClinicalAccess) -> &NoteVersion
```

The result is a reference, so it must not outlive whatever it points into.
There are two input references here, but no lifetime is written. The
*elision rules* fill them in: when a method takes `&self`, an output
reference gets the lifetime of `self`. Written out, it is:

```rust,ignore
pub fn current<'a, 'b>(&'a self, _access: &'b ClinicalAccess) -> &'a NoteVersion
```

That's the right answer: the version lives inside the note, not inside the
access token. The token can be dropped while the version is still in use.

Book: [Lifetime Elision](https://doc.rust-lang.org/book/ch10-03-lifetime-syntax.html#lifetime-elision).

### The borrow checker guards the history

```rust,ignore
let current = note.current(&access);
note.correct(&access, "Mild fever, 38.2 C.", at).unwrap(); // error[E0502]
println!("{}", current.text());
```

`current` borrows `note` for as long as it is used. `correct` needs
`&mut note`, and Rust allows either many `&` or one `&mut`, never both at
once. So code can't hold on to a version while the note is being changed
under it. The module docs carry this as a `compile_fail` doctest.

Book: [Mutable References](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html#mutable-references).

### Explicit lifetimes and `use<..>`

```rust,ignore
pub fn history<'a>(
    &'a self,
    _access: &ClinicalAccess,
) -> impl Iterator<Item = &'a NoteVersion> + use<'a> {
    iter::once(&self.original).chain(&self.corrections)
}
```

`history` returns an iterator that borrows the note. `'a` names that
borrow, so the signature can say the items live as long as `&self`.

`impl Iterator` hides the concrete type
(`Chain<Once<&NoteVersion>, slice::Iter<NoteVersion>>`). In edition 2024,
such a hidden type is assumed to *capture* every lifetime in scope,
including the one on `_access`. Then the iterator would keep the access
token borrowed too. `+ use<'a>` (*precise capturing*) says it holds only
`'a`.

Book: [Validating References with Lifetimes](https://doc.rust-lang.org/book/ch10-03-lifetime-syntax.html)
and [Returning Types That Implement Traits](https://doc.rust-lang.org/book/ch10-02-traits.html#returning-types-that-implement-traits).
Reference: [Precise capturing](https://doc.rust-lang.org/reference/types/impl-trait.html#precise-capturing).

### A borrowed `&str` in, a borrowed `&str` out

```rust,ignore
fn non_empty(text: &str) -> Result<&str, NoteError> {
    let text = text.trim();
    // ...
    Ok(text)
}
```

`trim` doesn't copy: it returns a slice of the same string. With one input
reference, elision ties the output to it. `write` and `correct` copy the
text with `to_owned` only once all the checks have passed.

Book: [String Slices](https://doc.rust-lang.org/book/ch04-03-slices.html#string-slices).

### The capability as a parameter

```rust,ignore
pub fn write(access: &ClinicalAccess, patient: PatientId, text: &str, at: DateTime<Utc>)
    -> Result<Self, NoteError>
```

This is the payoff of step 1.7. Without a `ClinicalAccess`, which only a
practitioner's role can be granted, none of these functions can be called.
The author is read from `access.practitioner()`, so a caller can't write a
note under someone else's name.

## Design choices worth questioning

- **Only the author can correct.** This follows common practice for medical
  records. A colleague who disagrees would add their own note. The
  alternative, any practitioner corrects, is simpler and still traceable,
  since each version records its author.
- **Every version records an author, but they're all the same.** With
  author-only corrections, `author` is the same in every version. Keeping it
  on the version means the rule can be relaxed later without changing the
  history's shape.
- **Reads take a token they don't use.** `current` and `history` ignore
  `_access`. Its job is to make the call impossible without the check. In M5
  it will also say who read the note, for the audit log.
- **`patient()` needs no access.** It names whose record this is, not what
  it says. Code that routes or lists notes can use it. One could argue that
  even knowing a patient has a note is clinical, and gate it too.
- **Unchanged corrections are refused.** A version that changes nothing
  would add noise to the history. A real system may want to allow "I
  confirmed this" entries, which would be a different operation.
- **The time is passed in.** As everywhere in the domain, there's no clock.
  `correct` refuses a time before the current version, so the history stays
  in order. The same instant is allowed.
- **No deletion.** A note can't be removed. How that fits with a patient's
  right to have their data deleted is a question for M7.
- **Notes don't link to an appointment.** A visit usually produces a note,
  but nothing needs that link yet.

## Tests

Writing records the trimmed text, the author from the token, the time and
the patient, and refuses blank text. A correction adds a version: the
original stays first and unchanged, and `history` lists every version
oldest first. Any practitioner can read a note, but only the author can
correct it, and that check comes before the others. Corrections that are
blank, unchanged or dated before the latest version are refused, and leave
the note unchanged. Errors have readable messages and implement `Error`.
Two `compile_fail` doctests prove the fields are private, and that a
borrowed version can't be held across a correction.
