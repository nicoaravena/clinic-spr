# 2.2 The practitioner's agenda

## Goal

Read a practitioner's appointments for a span of time, the way
`GET /practitioners/{id}/agenda` will in step 2.5. This is the first
*query*: it reads through a port and changes nothing. Booking was the
write side; this is the read side.

Roadmap row: *`practitioner_agenda` query (appointments in a UTC range)*.
Concepts: iterators over borrowed data, `impl Trait` returns.

## What changed

- `crates/domain`: `Schedule::appointments_in(range)` returns the
  appointments that overlap a range, as an iterator of references. See
  [schedule](../reference/schedule.md).
- `crates/app`: a new module, `src/agenda.rs`, with `practitioner_agenda`,
  `AgendaQuery` and `AgendaError`. See [app](../reference/app.md).
- Tests: eight new cases in `crates/domain/tests/schedule.rs`, and a new
  `crates/app/tests/agenda.rs`.
- `crates/clinic`: adds the `[2.2]` part of the day.

## Rust concepts

### Iterators over borrowed data

```rust,ignore
pub fn appointments_in(&self, range: TimeSlot) -> impl Iterator<Item = &Appointment> {
    self.appointments
        .iter()
        .skip_while(move |appointment| appointment.slot().end() <= range.start())
        .take_while(move |appointment| appointment.slot().start() < range.end())
}
```

`self.appointments.iter()` doesn't copy anything. It yields `&Appointment`,
a reference into the schedule's own `Vec`. The iterator therefore borrows
the schedule: while it's alive, the schedule can't be changed (no `book`),
and it can't outlive the schedule. The borrow checker enforces both.

The three kinds of iteration over a collection differ in what they hand
out:

| Call | Yields | The collection afterwards |
|---|---|---|
| `.iter()` | `&T` | unchanged, still usable |
| `.iter_mut()` | `&mut T` | changed in place, still usable |
| `.into_iter()` | `T` | consumed, gone |

`skip_while` and `take_while` are *iterator adapters*: each wraps an
iterator and returns another one. Nothing runs until someone pulls items
out, with `for`, `collect` or `next`. Iterators are lazy.

Book: [Processing a Series of Items with Iterators](https://doc.rust-lang.org/book/ch13-02-iterators.html).

### Returning `impl Trait`

The real type of that iterator is something like
`TakeWhile<SkipWhile<slice::Iter<'_, Appointment>, {closure}>, {closure}>`.
The closure types have no name you can write, so the signature couldn't
spell it out even if we wanted to. `impl Iterator<Item = &Appointment>`
says "some iterator of appointment references" and hides the rest. Callers
can use every `Iterator` method, but can't depend on the concrete type, so
it can change without breaking them.

The two alternatives:

- **Return `Vec<&Appointment>`.** Simple, but it allocates and walks the
  whole range even if the caller only wants the first item.
- **Return `Box<dyn Iterator<Item = &Appointment> + '_>`.** Also hides the
  type, but allocates the iterator on the heap and calls through a vtable
  (the dynamic dispatch from step 2.1). Needed only when one function must
  return different iterator types from different branches.

`impl Trait` costs nothing at runtime: the compiler knows the concrete type
and calls it directly.

The returned iterator borrows `self`, but the signature doesn't say so.
In edition 2024 an `impl Trait` return captures every lifetime in scope,
here the one of `&self`. Step 1.8 needed `+ use<'a>` to *leave out* a
lifetime (the access token's); this method has nothing to leave out,
because `range` is a `TimeSlot`, which holds no references.

Book: [Returning Types That Implement Traits](https://doc.rust-lang.org/book/ch10-02-traits.html#returning-types-that-implement-traits).

### `move` closures

The two closures use `range`, which lives on the stack of
`appointments_in`. That function returns before the closures ever run, so
they can't borrow it. `move` makes each closure keep its own copy. A
`TimeSlot` is `Copy`, so both closures get one and nothing is "moved away".

Without `move`, the compiler refuses: the closure may outlive the borrowed
`range`.

Book: [Capturing References or Moving Ownership](https://doc.rust-lang.org/book/ch13-01-closures.html#capturing-references-or-moving-ownership).

### `skip_while` and `take_while` lean on an invariant

A plain `filter(|a| a.slot().overlaps(&range))` would also be correct. It
checks every appointment the practitioner ever had, though, and the
schedule already guarantees more than `filter` needs:

- Appointments are sorted by start (`book` inserts at the sorted position).
- They never overlap (`book` refuses overlaps).

Together these mean the ends are sorted too. So every appointment that ends
before the range comes first, and `skip_while` drops those. After that,
`take_while` stops at the first appointment starting at or after the
range's end: nothing later can overlap it either. The walk never looks past
the range.

The tests `back_to_back_appointments_are_not_in_the_range` and
`appointments_straddling_either_edge_are_in_the_range` pin down both edges.

Reference: [`Iterator::skip_while`](https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.skip_while),
[`Iterator::take_while`](https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.take_while).

### From borrowed to owned at the use-case boundary

```rust,ignore
let schedule = schedules
    .get(query.clinic, query.practitioner)
    .ok_or(AgendaError::UnknownPractitioner)?;

Ok(schedule.appointments_in(query.range).cloned().collect())
```

`get` returns an owned `Schedule`, a local variable that is dropped when
`practitioner_agenda` returns. An iterator borrowing it can't be returned:
it would point into freed memory, and the compiler says so ("returns a
value referencing data owned by the current function"). So the use case
copies the appointments out:

- `.cloned()` turns each `&Appointment` into an `Appointment`.
- `.collect()` gathers them into the return type, `Vec<Appointment>`. The
  type in the signature tells `collect` what to build.

The domain hands out borrows and lets the caller decide whether to copy.
The use case is the caller that must, because its data doesn't outlive it.

Book: [Methods that Produce Other Iterators](https://doc.rust-lang.org/book/ch13-02-iterators.html#methods-that-produce-other-iterators).

## Design choices worth questioning

- **"In the range" means overlaps.** An appointment from 11:45 to 12:15
  shows up in the agenda for 12:00-13:00. A calendar wants that. The other
  reading, "starts within the range", would hide an appointment that is
  already running when the range starts.
- **The range is a `TimeSlot`.** It already guarantees start before end, so
  an empty or reversed range can't reach the use case. The name fits less
  well: a slot is usually something you book. A separate `TimeRange` type
  would read better but repeat the same code.
- **The query returns a `Vec`, not an iterator.** Forced by `get` returning
  an owned schedule, as above. A port that hands out borrows (`fn get(&self,
  ..) -> Option<&Schedule>`) would avoid the copy, but no database adapter
  can implement it: the rows it loads live only as long as the call.
- **The port is unchanged.** The query loads the whole schedule and filters
  it in the domain. A database would rather run `WHERE start < $end AND
  end > $start`. That needs a new port method, and it belongs with the
  database adapter in M3, where the cost is real.
- **Same error message as booking.** `AgendaError::UnknownPractitioner` and
  `BookAppointmentError::UnknownPractitioner` read the same, and the API
  will map both to 404. They are separate types so each use case lists only
  the failures it can have.
- **Any role can read any practitioner's agenda.** `ScheduleAccess` is
  granted to every role, so a practitioner can read a colleague's agenda.
  Receptionists need that. Whether practitioners should is open.
- **An empty agenda is `Ok(vec![])`.** A practitioner with nothing booked is
  a normal answer, not an error.

## Tests

`crates/domain/tests/schedule.rs`: an empty schedule has nothing in any
range. Appointments in a range come back sorted by start, and ones outside
it are left out. An appointment ending exactly at the range's start, or
starting exactly at its end, isn't in it; one straddling either edge is. A
range inside one appointment returns it. A range with no appointments
returns nothing. Asking twice gives the same answer and leaves the schedule
unchanged.

`crates/app/tests/agenda.rs`: the agenda holds the appointments in the
range with their patient, type, slot and status, sorted by start, and
leaves out the rest. A range with no appointments gives an empty agenda. An
unknown practitioner and another clinic's practitioner are both refused as
`UnknownPractitioner`. The query accepts a trait object. The error has a
readable message and implements `std::error::Error`.

## See it run

```sh
cargo run -p clinic
```

A receptionist books a follow-up for a second patient at 13:00, then reads
Ana's agenda for four ranges. The 10:15-13:15 range shows the 10:00
consultation that was already running when it starts. The lunch break has
no appointments, and clinic 2 can't read Ana's agenda at clinic 1. Earlier
sections are unchanged. New output:

```text
[2.2] Agenda
  Clinic 1 books Follow-up with practitioner 1 at 13:00 for patient 2: booked for 13:00-13:15
  Agenda for practitioner 1 at clinic 1, 09:00-12:00:
    10:00-10:30 Consultation for patient 1
  Agenda for practitioner 1 at clinic 1, 10:15-13:15:
    10:00-10:30 Consultation for patient 1
    13:00-13:15 Follow-up for patient 2
  Agenda for practitioner 1 at clinic 1, 12:00-13:00: no appointments
  Agenda for practitioner 1 at clinic 2, 09:00-17:00: refused: clinic has no schedule for that practitioner
```
