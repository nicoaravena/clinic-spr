# 2.4 The HTTP API: booking over `POST /appointments`

## Goal

Put the first HTTP edge in front of the booking use case. A client sends
JSON naming a practitioner, a patient, an appointment type and a start
time, and says which clinic it is acting for in an `X-Clinic-Id` header.
The API books through `book_appointment` from step 2.1 and answers with the
appointment, or with an error whose status code says what went wrong.

The API is a library. Nothing opens a socket yet: the tests send requests
straight into the router. In step 2.5 the `clinic` binary starts serving it.

Roadmap row: *`api` crate: axum, `POST /appointments` with `X-Clinic-Id`,
serde DTOs, domain errors to HTTP status codes*. Concepts: async/await,
tokio, `Arc<Mutex<_>>`, `Send`/`Sync`, extractors, serde.

## What changed

- A new crate, `crates/api` (`clinic-api`). See [api](../reference/api.md).
  - `lib.rs`: `router`, which builds the axum `Router`.
  - `state.rs`: `AppState`, the storage every request shares.
  - `clinic_header.rs`: `ClinicHeader`, an extractor for `X-Clinic-Id`.
  - `appointments.rs`: the handler `book` and the JSON shapes
    `BookAppointmentBody` and `AppointmentBody`.
  - `error.rs`: `ApiError`, which picks the status code and writes the JSON
    error body.
- New dependencies, all in `crates/api` only: `axum` 0.8, `serde` 1 with
  `derive`, `thiserror` 2, and chrono's `serde` feature. For tests only:
  `tokio` 1, `tower` 0.5, `http-body-util` 0.1 and `serde_json` 1.
- Tests: a new `crates/api/tests/appointments.rs` with 15 cases.
- The domain and `app` are unchanged. So is the `clinic` binary: its
  scripted day stays as it was until step 2.5 turns it into the server.
- [Roadmap](../roadmap.md): a new step 2.6 for an endpoint that sets a
  practitioner's weekly hours. Step 2.3 had pencilled that in for 2.4.

## Rust concepts

### `async fn` and futures

```rust,ignore
pub async fn book(
    State(state): State<AppState>,
    ClinicHeader(clinic): ClinicHeader,
    body: Result<Json<BookAppointmentBody>, JsonRejection>,
) -> Result<(StatusCode, Json<AppointmentBody>), ApiError> {
```

Calling an `async fn` doesn't run it. It returns a *future*: a value that
holds the function's state and makes progress each time something *polls*
it. Inside, `.await` is where the function can pause, for example to wait
for more bytes from the network, and let the thread serve another request
in the meantime. That's how one thread can juggle thousands of
connections.

Futures need something to poll them, which is the *runtime*. Rust doesn't
ship one. This project uses **tokio**, which axum is built on. Notice that
`book` has no `.await` at all: booking in memory never waits. It's `async`
because axum requires handlers to be. The database adapters in M3 will
`.await`.

The tests need a runtime too, and `#[tokio::test]` starts one per test.
`#[tokio::test(flavor = "multi_thread", worker_threads = 4)]` starts a
runtime with four threads, which the concurrency test needs.

Book: [Fundamentals of Asynchronous Programming](https://doc.rust-lang.org/book/ch17-00-async-await.html).
Reference: [tokio tutorial](https://tokio.rs/tokio/tutorial).

### axum: router, handlers and extractors

```rust,ignore
pub fn router(state: AppState) -> Router {
    Router::new()
        .route("/appointments", post(appointments::book))
        .with_state(state)
}
```

A *handler* is an async function whose parameters are all *extractors*.
Each extractor knows how to build itself from the request:

| Parameter | Reads | Fails with |
|---|---|---|
| `State(state): State<AppState>` | the state passed to `with_state` | never |
| `ClinicHeader(clinic): ClinicHeader` | the `X-Clinic-Id` header | `ApiError::MissingClinic`, `InvalidClinic` |
| `Result<Json<BookAppointmentBody>, JsonRejection>` | the body, as JSON | never: the error is handed to the handler |

axum runs the extractors in order before the handler. If one fails, its
*rejection* becomes the response and the handler never runs. The body can
only be read once, so the extractor that reads it (`Json`) must come last.

The patterns `State(state)` and `ClinicHeader(clinic)` destructure the
newtype right in the parameter list, the same way `let` can. They're the
newtypes from step 1.2 with a pattern on the outside.

Reference: [axum's handler docs](https://docs.rs/axum/0.8/axum/handler/index.html),
[extractors](https://docs.rs/axum/0.8/axum/extract/index.html).
Book: [Destructuring structs](https://doc.rust-lang.org/book/ch19-03-pattern-syntax.html#destructuring-structs).

### Writing an extractor: `FromRequestParts`

```rust,ignore
impl<S> FromRequestParts<S> for ClinicHeader
where
    S: Send + Sync,
{
    type Rejection = ApiError;

    async fn from_request_parts(parts: &mut Parts, _state: &S) -> Result<Self, Self::Rejection> {
        let value = parts.headers.get(CLINIC_HEADER).ok_or(ApiError::MissingClinic)?;
        let id = value
            .to_str()
            .ok()
            .and_then(|text| text.parse::<u64>().ok())
            .ok_or(ApiError::InvalidClinic)?;

        Ok(Self(ClinicId::new(id)))
    }
}
```

`FromRequestParts` is for extractors that need only the head of the
request (method, URI, headers), not the body. Implementing it is all it
takes for `ClinicHeader` to work as a handler parameter. `type Rejection`
is an *associated type*: each implementation chooses what its errors are,
like `Capability::NAME` chose a constant in step 1.7.

`to_str` fails if the header isn't visible ASCII, and `parse::<u64>` fails
on `"abc"`, `"-1"`, `"1.5"` and `""`. `.ok()` turns both `Result`s into
`Option`s so they chain with `and_then`, and one `ok_or` maps every failure
to the same error.

Since Rust 1.75 a trait can have an `async fn` in it, and axum 0.8 uses
that. Older axum needed the `async-trait` macro here.

This extractor is where M4 makes its change: the clinic will come from the
caller's token, and the handler's signature won't need to change.

Reference: [`FromRequestParts`](https://docs.rs/axum/0.8/axum/extract/trait.FromRequestParts.html).
Book: [Associated types](https://doc.rust-lang.org/book/ch20-02-advanced-traits.html#associated-types).

### Taking a rejection as a `Result`

When `Json` fails, axum answers with plain text. Every other error here is
JSON, so the handler asks for `Result<Json<_>, JsonRejection>` instead. That
extractor never fails, and the handler decides what to do:

```rust,ignore
let Json(body) = body?;
```

`?` works because `ApiError` implements `From<JsonRejection>`. It keeps
the status axum chose: 400 for malformed JSON, 415 for a missing
`Content-Type: application/json`, and 422 for a missing, mistyped or
unknown field.

### serde: data transfer objects

```rust,ignore
#[derive(Debug, Clone, PartialEq, Eq, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct BookAppointmentBody {
    pub practitioner_id: u64,
    pub patient_id: u64,
    pub appointment_type: String,
    pub start: DateTime<Utc>,
}
```

`#[derive(Deserialize)]` writes the code that reads this struct from JSON
(or any format serde supports). The field names are the JSON keys.
`deny_unknown_fields` refuses `{"room": 3}`, so a client's typo shows up as
an error instead of being ignored.

`start` is a `DateTime<Utc>`, and chrono's `serde` feature teaches it to
read RFC 3339 text. `"2026-03-02T07:00:00-03:00"` is read as 10:00 UTC, so
a client may send its local offset and the domain still sees only UTC.

These structs are *DTOs* (data transfer objects): they describe the wire
format and nothing else. The domain types don't derive serde. That keeps
`clinic-domain` free of a serialization library, and lets the JSON shape
and the domain change separately. The cost is the copying in
`AppointmentBody::new`, and a hand-written `status_name` for the status
enum.

Reference: [serde derive](https://serde.rs/derive.html),
[container attributes](https://serde.rs/container-attrs.html).

### Sharing state: `Arc<Mutex<_>>`

```rust,ignore
#[derive(Clone)]
pub struct AppState {
    store: Arc<Mutex<Store>>,
}

pub(crate) struct Store {
    pub(crate) schedules: Box<dyn ScheduleRepository + Send>,
    pub(crate) types: Box<dyn AppointmentTypes + Send>,
}
```

Every request needs the same storage, and several may run at once on
different threads. Two wrappers make that safe:

- `Arc` (atomically reference-counted) lets many owners hold one value.
  Cloning an `Arc` copies a pointer and bumps a counter. The value is
  dropped when the last clone goes. axum clones the state for each request.
- `Mutex` lets one owner at a time reach the value. `lock()` waits until no
  one else holds it and returns a *guard*. Dropping the guard unlocks.

Rust won't let you skip either. `ScheduleRepository::save` takes
`&mut self`, and an `Arc` only hands out `&`, so the code can't change the
schedules without a lock.

The ports are trait objects (`Box<dyn ...>`, step 2.1), so `AppState`
and `Router` aren't generic. `book_appointment` takes `S: ?Sized`, so
`store.schedules.as_mut()`, a `&mut dyn ScheduleRepository`, fits it as is.

Book: [Shared-State Concurrency](https://doc.rust-lang.org/book/ch16-03-shared-state.html).

### Holding the lock for the whole use case

```rust,ignore
let mut store = state.lock()?;
let store = &mut *store;
let appointment = book_appointment(
    store.schedules.as_mut(),
    store.types.as_ref(),
    &access,
    request,
)?;
```

`book_appointment` reads the schedule, books into a copy, and saves the
copy. If the lock were released between the read and the save, two
requests could both read a free 10:00, both book it, and the second save
would silently replace the first. That's a *lost update*. Holding the
guard for the whole call makes it one step. A test sends 20 identical
requests at once on four threads and expects exactly one `201`.

`let store = &mut *store;` turns the guard into a plain `&mut Store`.
Through that, the compiler can see that `schedules` (borrowed `&mut`) and
`types` (borrowed `&`) are different fields, so it allows both borrows at
once. Through the guard itself, every field access goes through
`DerefMut`, which borrows the whole guard.

This is `std::sync::Mutex`, not tokio's. tokio's own docs recommend the std
one when the lock is never held across an `.await`, as here. It's faster,
and the compiler enforces the rule (next section).

`lock()` fails if a thread panicked while holding the lock: the data might
be half-changed, so the mutex is *poisoned*. `AppState::lock` turns that
into `ApiError::Internal`, a 500.

### `Send` and `Sync`

- `Send`: a value can be *moved* to another thread.
- `Sync`: a value can be *shared* by reference between threads.

The compiler works these out from a type's fields and checks them
wherever a value crosses threads. tokio may move a request's future from
one thread to another between polls, so axum requires every handler's
future to be `Send`. That's why the trait objects say `+ Send`, and why
`AppState::new` asks for `S: Send + 'static`. `Mutex<T>` is `Sync` when
`T` is `Send`, which makes `Arc<Mutex<Store>>` shareable. A test checks
`AppState: Clone + Send + Sync + 'static` at compile time:

```rust,ignore
fn assert_shareable<T: Clone + Send + Sync + 'static>() {}

assert_shareable::<AppState>();
```

A std `MutexGuard` is *not* `Send`: on some platforms a lock must be
released by the thread that took it. If `book` held the guard across an
`.await`, its future would hold the guard, the future wouldn't be `Send`,
and `post(appointments::book)` would fail to compile. axum's error for that
is notoriously unhelpful (a missing `Handler` implementation), and
`#[axum::debug_handler]` exists to explain it.

Book: [Extensible Concurrency with `Send` and `Sync`](https://doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html).

### Errors become responses: `IntoResponse`

```rust,ignore
impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let body = ErrorBody {
            error: self.code(),
            message: self.to_string(),
        };

        (self.status(), Json(body)).into_response()
    }
}
```

A handler can return anything that implements `IntoResponse`. A
`(StatusCode, Json<T>)` tuple does, and so does `Result<T, E>` when both
sides do. That's why `book` can return `Result<_, ApiError>` and use `?`
throughout. Each `?` converts with `From`: `JsonRejection`,
`AccessDenied` and `BookAppointmentError` each have a `From` impl, the last
two generated by thiserror's `#[from]`.

`status` and `code` match on the nested `BookingError` without a wildcard
`_`. If the domain adds a new way to refuse a booking, this crate stops
compiling until someone decides its status code.

Reference: [axum error handling](https://docs.rs/axum/0.8/axum/error_handling/index.html).

### Testing without a socket: `oneshot`

```rust,ignore
let response = app.oneshot(request).await.unwrap();
```

An axum `Router` is a tower `Service`: something that takes a request and
returns a future of a response. `ServiceExt::oneshot` sends it a single
request directly. There's no port to bind, no network, and nothing to
clean up, yet the request still goes through routing, every extractor, the
handler and `IntoResponse`. `http-body-util` collects the streamed body
into bytes, and `serde_json` parses it for the assertions.

## Design choices worth questioning

- **Everyone acts as a receptionist.** There's no login before M4, so
  `book` grants `ScheduleAccess` from a constant `STAND_IN_CALLER`. Every
  role may manage schedules, so no outcome changes. The `?` on the grant and
  the `403 access_denied` mapping are already in place for when the role
  comes from a token.
- **Unknown IDs in the body are 422, not 404.** The URL `/appointments`
  exists; what's wrong is a reference inside the body. Many APIs answer
  404 here anyway. Step 2.5's `GET /practitioners/{id}/agenda` will answer
  404, because there the ID is the path.
- **An overlap is 409, other refusals 422.** 409 Conflict says the request
  was fine but clashes with the current state, and retrying with another
  time may work. "Outside working hours" is also about state, but it reads
  as invalid input, so it's 422. That's a judgment call.
- **One lock for the whole store.** Bookings for different practitioners,
  even at different clinics, wait for each other. In memory that's
  microseconds. In M3 Postgres takes over: a transaction per request, and
  an exclusion constraint as the last line of defense.
- **A rejected tenant isn't told apart from a missing practitioner.**
  Clinic 2 asking for clinic 1's practitioner gets `unknown_practitioner`,
  exactly as if the practitioner didn't exist. That's deliberate: a
  different answer would let one clinic probe another's data.
- **No `Location` header and no appointment ID.** A `201 Created` usually
  points to the new resource. Appointments have no identity yet, so the
  response echoes the appointment instead. An ID arrives when something
  needs to name one appointment, such as cancelling it.
- **The error `message` is for people.** It comes from the error's
  `Display`, and for a bad body from axum's own text, which can change
  between axum versions. Clients should match on `error`.
- **`tokio` is only a test dependency.** The library never names tokio.
  axum pulls it in, and the binary will start the runtime in step 2.5.
- **chrono's `serde` feature is on for the whole workspace build.** Cargo
  unifies features, so `clinic-domain` compiles against a chrono with serde
  support when the workspace is built together. The domain code still
  never uses serde, and builds without it on its own.
- **The concurrency test can miss a regression.** If someone split the
  lock, the gap between read and save would be a few microseconds, and 20
  requests may not hit it on every run. The test documents the guarantee
  and catches it most of the time; the comment in `book` explains why the
  lock spans the call.

## Tests

`crates/api/tests/appointments.rs` seeds clinic 1 with practitioner 1
working 09:00-12:00 UTC and a 30-minute "Consultation", and clinic 2 with
the same type but no schedules.

A valid booking answers 201 with the appointment as JSON, its end computed
from the type, and status `scheduled`. Sending it again answers 409, which
shows it was saved. A start written with a `-03:00` offset is stored and
returned as the same instant in UTC.

Headers: no `X-Clinic-Id` is 400 `missing_clinic_id`, and `abc`, `-1`,
`1.5` and an empty value are 400 `invalid_clinic_id`. Clinic 2 can't book
into clinic 1's practitioner: 422 `unknown_practitioner`.

Booking rules: an unknown type is 422 `unknown_appointment_type`, a booking
running past the end of the shift is 422 `outside_working_hours`, and an
overlap is 409 with the exact JSON error body.

Bodies: malformed JSON is 400, a missing field, a mistyped field, an
unknown field or a start that isn't a timestamp is 422, and no JSON content
type is 415, all with `invalid_body` and a non-empty message.

Twenty concurrent identical bookings on four threads give one 201 and
nineteen 409s. A table checks every `ApiError` variant's status and code,
including `access_denied` (403) and `internal` (500), which the handler
can't reach today. `AppState` is checked to be `Clone + Send + Sync`.
