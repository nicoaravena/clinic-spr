# 2.3 Weekly hours and daylight saving

## Goal

Let a clinic describe a practitioner's hours the way people do, as a week
of local times ("Monday to Friday, 09:00-13:00, in Santiago"), and turn
that into the dated UTC shifts the domain's `WorkingHours` needs. Since
step 1.5 the domain has only known UTC, and something at the edge had to
do this conversion. Daylight saving is the hard part: on two nights a year
some local times don't exist, and some happen twice.

Roadmap row: *Weekly template to dated UTC shifts in the clinic's time
zone, daylight saving included (adds `chrono-tz`)*. Concepts: `chrono-tz`,
`LocalResult`, ambiguous and missing local times.

## What changed

- `crates/app`: a new module, `src/weekly_hours.rs`, with `WeeklyShift`,
  `WeeklyHours` and `WeeklyHoursError`. See [app](../reference/app.md).
  Depends on a new crate, `chrono-tz`.
- Tests: a new `crates/app/tests/weekly_hours.rs` with 24 cases.
- `crates/clinic`: depends on `chrono-tz`, and adds the `[2.3]` part of
  the day.
- The domain is unchanged. It still only sees UTC.

## Rust concepts

### Adding an external crate

```toml
[dependencies]
chrono = { version = "0.4", default-features = false, features = ["std"] }
chrono-tz = "0.10"
```

`"0.10"` means "any 0.10.x": Cargo treats the first non-zero number as the
major version, so it accepts compatible updates and refuses 0.11. The exact
version it picked (0.10.4) is recorded in `Cargo.lock`, so every build uses
the same one until someone runs `cargo update`.

`chrono-tz` compiles the IANA time zone database (tzdata) into the binary.
There's no file to read at runtime and nothing to install on the server.
The price is that a government changing its clock rules needs a new crate
version and a redeploy.

Book: [Using a Crate to Get More Functionality](https://doc.rust-lang.org/book/ch02-00-guessing-game-tutorial.html#using-a-crate-to-get-more-functionality),
[Cargo: specifying dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html).

### Naive and zoned types

chrono splits time into two families:

| Type | What it is | Example |
|---|---|---|
| `NaiveTime`, `NaiveDate`, `NaiveDateTime` | A reading on a clock or calendar, with no time zone | "09:00", "2026-04-06 09:00" |
| `DateTime<Tz>` | An instant, plus the zone to show it in | 2026-04-06 09:00 in Santiago |
| `DateTime<Utc>` | An instant, shown in UTC | 2026-04-06 13:00 UTC |

A weekly template is naive on purpose: "09:00 on Mondays" is a clock
reading, and which instant it means depends on the date. The domain uses
only `DateTime<Utc>`. The types keep the two apart: you can't compare a
`NaiveDateTime` with a `DateTime<Utc>`, so forgetting to convert doesn't
compile.

`Tz` is a plain `enum` with one variant per zone (`Tz::America__Santiago`,
re-exported as `chrono_tz::America::Santiago`). It's `Copy`, so
`WeeklyHours::time_zone` returns it by value.

Reference: [chrono's overview](https://docs.rs/chrono/0.4/chrono/#overview).

### Matching on `LocalResult`

Converting a clock reading to an instant can give one answer, two or none,
and chrono's return type says so:

```rust,ignore
fn to_utc(time_zone: Tz, local: NaiveDateTime) -> DateTime<Utc> {
    match time_zone.from_local_datetime(&local) {
        LocalResult::Single(instant) => instant.with_timezone(&Utc),
        LocalResult::Ambiguous(earliest, _latest) => earliest.with_timezone(&Utc),
        LocalResult::None => gap_end(time_zone, local),
    }
}
```

- `Single`: the usual case.
- `Ambiguous(earliest, latest)`: the clocks went back, and this reading
  happens twice. In Santiago on 2026-04-04, 23:30 happens at 02:30 UTC and
  again at 03:30 UTC.
- `None`: the clocks jumped over this reading. In Santiago, 2026-09-06
  00:30 never happens.

This is the same idea as `Option` and `Result` from earlier steps: the type
lists every outcome, and `match` must handle all three. A library that
returned a plain `DateTime` would have to guess silently. chrono makes the
caller choose, and the choice is written down here. `_latest` names the
value being ignored; the leading underscore stops the unused-variable
warning.

chrono also has shortcuts, `.single()` and `.earliest()`, that turn the
result into an `Option`. They would hide the `None` case, which is the one
this step had to think about.

Book: [The `match` Control Flow Construct](https://doc.rust-lang.org/book/ch06-02-match.html).
Reference: [`LocalResult`](https://docs.rs/chrono/0.4/chrono/offset/enum.LocalResult.html).

### Finding the end of a gap with `successors` and `find`

For `None`, the rule is "the instant the clocks jump to". chrono doesn't
say when that is, so `gap_end` searches for it:

```rust,ignore
std::iter::successors(Some(earliest), |instant| {
    Some(*instant + TimeDelta::seconds(1))
})
.take_while(|instant| *instant <= latest)
.find(|instant| instant.with_timezone(&time_zone).naive_local() >= local)
.unwrap_or(latest)
```

`successors` builds an iterator from a first value and a closure that
makes the next one: here, one second after another, without end.
`take_while` bounds it, and `find` stops at the first instant whose clock
reading has passed `local`. Because iterators are lazy (step 2.2), only the
seconds up to the answer are ever made.

The window `earliest..=latest` is `local` read with the offset after the
gap and with the offset before it, which are exactly the gap's length
apart. That's one hour (3600 steps) for ordinary daylight saving, and the
search runs only on the two change nights a year.

Reference: [`std::iter::successors`](https://doc.rust-lang.org/std/iter/fn.successors.html),
[`Iterator::find`](https://doc.rust-lang.org/std/iter/trait.Iterator.html#method.find).

### Walking dates with `iter_days`

```rust,ignore
for date in from.iter_days().take_while(|date| *date < until) {
```

`NaiveDate::iter_days` yields `from`, the next day, and so on. The range is
half-open like every range in this project: `from` is included, `until`
isn't. If `until` isn't after `from`, `take_while` stops at once and the
result is empty, with no special case.

### Changing the last item in place: `last_mut` and match guards

```rust,ignore
match shifts.last_mut() {
    Some(previous) if previous.end() == start => {
        *previous = TimeSlot::new(previous.start(), end)
            .expect("a shift's end is after its start");
    }
    _ => shifts
        .push(TimeSlot::new(start, end).expect("a shift's end is after its start")),
}
```

`last_mut` returns `Option<&mut TimeSlot>`: a mutable borrow of the last
shift, if there is one. `if previous.end() == start` is a *match guard*:
the arm matches only if the pattern fits and the condition holds. Writing
through `*previous` replaces the last shift with a longer one. The borrow
ends with that arm, so the other arm can `push`.

Book: [Extra Conditionals with Match Guards](https://doc.rust-lang.org/book/ch19-03-pattern-syntax.html#extra-conditionals-with-match-guards).

### `expect` for invariants

`working_hours` returns `WorkingHours`, not a `Result`, and calls
`TimeSlot::new` and `WorkingHours::new` with `.expect(..)`. Both can fail
in general, but not here: the conversion never maps a later local time to
an earlier instant, the template's shifts are separated, and empty shifts
are dropped before they reach `TimeSlot::new`. A `Result` would make every
caller handle an error that can't happen.

`expect` is `unwrap` with a message saying why it can't fail. If the
reasoning is ever wrong, the program stops with that message instead of
carrying on with bad data. The year-long test in three zones is there to
catch that.

Book: [Shortcuts for Panic on Error](https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html#shortcuts-for-panic-on-error-unwrap-and-expect).

## Design choices worth questioning

- **Skipped times move to the jump; repeated times take the first
  occurrence.** A shift written as 02:30-05:00 on Madrid's spring-forward
  night starts when the clocks show 03:00. The alternatives:
  - iCalendar (RFC 5545) reads a skipped time with the offset before the
    gap, so 02:30 becomes 03:30. That's what calendar apps do, but it can
    put a shift's end before its start (02:30-03:15 would end at 03:15,
    before 03:30).
  - Refusing to expand would fail one week a year for a template that's
    fine the other 51, and someone would have to fix it by hand.

  The chosen rules never move a later time to an earlier instant, which is
  what makes expansion unable to fail.
- **Shifts lost to a skipped hour are dropped; shifts that end up touching
  are merged.** Both follow from the rule above. Merging is what
  `WorkingHours` already asks for ("09-12 and 12-17 must be written as
  09-17").
- **No shifts that cross midnight.** `WeeklyShift::new` refuses an end
  before the start, so a 22:00-06:00 night shift must be written as two
  shifts, 22:00-23:59 and 00:00-06:00 the next day, which leaves a
  gap of under a minute at midnight. Clinics rarely need more; supporting it
  means an end on the next day and a template that spans weeks.
- **The module lives in `app`, not the domain.** The roadmap keeps time
  zones at the edges, and the domain still has no time zone code. The
  weekly template is arguably a domain concept, though, and it might move
  there later as naive times, with only the conversion staying outside.
- **`Tz` appears in the public API**, so `app` is tied to `chrono-tz`.
  Wrapping it in a `ClinicTimeZone` newtype would hide that, but there's
  nothing to validate yet: a `Tz` is always a valid zone. Parsing a name
  such as `"America/Santiago"` from a request happens in the API (step 2.4).
- **Expanded shifts are a snapshot.** If tzdata changes after shifts were
  expanded and saved, they keep the old offsets. Expanding close to when
  the hours are used keeps that window small.
- **Nothing calls it yet.** No use case expands hours or saves them in a
  schedule. The API decides when to expand, and how far ahead.
- **The gap search walks one second at a time.** A binary search would
  take 12 steps instead of up to 3600. The walk is simpler to read and
  runs twice a year per zone.

## Tests

`crates/app/tests/weekly_hours.rs`: a weekly shift keeps its weekday and
times, and must end after it starts on the same day. Shifts on the same
weekday can't overlap or touch, the same times on different weekdays are
fine, and shifts are stored sorted from Monday. No shifts, an empty range
and a reversed range all give no working hours. The range includes its
first date and excludes its last, and only dates on a template weekday get
shifts.

Time zones: the same Madrid hours move from 08:00 to 07:00 UTC across the
March change, and Santiago in March is three hours behind UTC. On Madrid's
spring-forward night a shift starting or ending in the skipped hour is
moved to the jump, one entirely inside it is dropped that day only, and two
separated only by it are merged. On the fall-back night a shift starting or
ending in the repeated hour uses its first occurrence. Santiago's changes
at midnight are checked both ways.

A whole year in Madrid, Santiago and Lord Howe (whose clocks change by half
an hour), with boundaries in every change window, expands without panicking
to sorted, separated shifts. Expanded hours plug into `Schedule::new`, and a
booking at 09:00 local lands at the right UTC instant. The error has
readable messages and implements `std::error::Error`.

## See it run

```sh
cargo run -p clinic
```

Ana's weekly hours are written in Santiago time and expanded around the
two 2026 changes. In April the clocks go back at midnight on Saturday:
Friday's 09:00 is 12:00 UTC and Monday's is 13:00 UTC, and Saturday's shift
ends at the first 23:30. In September midnight on Sunday doesn't exist, so
the 00:00-02:00 shift starts at 01:00 and lasts an hour. Earlier sections
are unchanged. New output:

```text
[2.3] Weekly hours
  Practitioner 1 works Mon-Fri 09:00-13:00 and 14:00-18:00, on call Sat 20:00-23:30 and Sun 00:00-02:00, in America/Santiago
  Clocks go back at the end of Sat 2026-04-04, so 23:00-24:00 happens twice:
    Fri 2026-04-03 09:00-13:00 at -03:00 is 12:00-16:00 UTC
    Fri 2026-04-03 14:00-18:00 at -03:00 is 17:00-21:00 UTC
    Sat 2026-04-04 20:00-23:30 at -03:00 is 23:00-02:30 UTC
    Sun 2026-04-05 00:00-02:00 at -04:00 is 04:00-06:00 UTC
    Mon 2026-04-06 09:00-13:00 at -04:00 is 13:00-17:00 UTC
    Mon 2026-04-06 14:00-18:00 at -04:00 is 18:00-22:00 UTC
  Clocks jump forward at the start of Sun 2026-09-06, so 00:00-01:00 doesn't exist:
    Sat 2026-09-05 20:00-23:30 at -04:00 is 00:00-03:30 UTC
    Sun 2026-09-06 01:00-02:00 at -03:00 is 04:00-05:00 UTC
```
